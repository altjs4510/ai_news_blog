## 📌 학습 정리

### 1. 한 줄로 말하면

인공지능 비서에게 외부 도구를 붙여주는 규칙(MCP)이 새 버전에서 "매번 인사부터 하고 대화를 트는 방식"을 버리고 "용건 한 번에 말하기"로 바뀌었고, 그 덕에 도구 만들기가 훨씬 쉬워졌다는 이야기입니다.

### 2. 왜 이게 만들어졌어요?

원래 AI 에이전트에게 새 기능을 붙이려면 **모델 컨텍스트 프로토콜(Model Context Protocol, MCP)**이라는 약속을 따랐는데, 이게 도구를 한 번 쓰려면 두 단계를 거쳐야 했습니다. 먼저 서버에 "나 이제 접속할게"라고 알려 세션 번호를 받고, 그 번호를 들고 다시 요청을 보내는 식이었죠. 서버 입장에선 누가 어떤 번호를 들고 있는지 계속 기억해둬야 하고, 서버가 여러 대면 같은 사람의 요청을 매번 같은 서버로 보내주는 처리까지 필요했습니다. 글쓴이는 이런 복잡함 때문에 한동안 MCP보다 "터미널과 인터넷 접근 권한을 그냥 주는" 방식에 관심이 옮겨갔다고 말합니다. 그런데 그 방식은 위험 부담이 크고 성능 좋은 모델이 아니면 다루기 어려워서, 감사(audit)하고 통제하기 쉬운 MCP 쪽으로 다시 눈이 갔다는 흐름입니다.

### 3. 비유로 풀면

예전 방식은 관공서 민원 창구 같았습니다. 먼저 번호표를 뽑고 "저 왔어요" 등록을 한 다음, 그 번호를 들고 다시 가서야 진짜 용건을 말할 수 있었죠. 창구 직원은 번호표별로 누가 누군지 계속 기억하고 있어야 했고요.

새 방식은 우편으로 서류 한 장 보내는 것에 가깝습니다. 봉투 겉면에 "누구에게, 무슨 용건으로"를 다 적어 보내니 상대가 나를 미리 기억할 필요가 없습니다. 그래서 결국 요청 한 번에 필요한 정보가 전부 담기고, 서버는 아무것도 기억하지 않아도 되니 만드는 쪽도 쓰는 쪽도 단순해집니다.

### 4. 어떻게 작동하는지 (그림으로)

```mermaid
flowchart TD
    subgraph OLD["예전 방식 — 세션을 기억하는 서버"]
        A1["AI 도구 쪽에서<br/>먼저 접속 신청"] --> A2["서버가 세션 번호<br/>발급하고 기억"]
        A2 --> A3["세션 번호를 들고<br/>다시 도구 실행 요청"]
        A3 --> A4["도구 실행 결과 반환"]
    end

    subgraph NEW["새 방식 — 아무것도 기억하지 않는 서버"]
        B1["요청 한 번에<br/>규격 버전·도구 이름·<br/>입력값을 모두 담아 전송"] --> B2["서버는 기억 없이<br/>바로 도구 실행"]
        B2 --> B3["도구 실행 결과 반환"]
    end
```

예전에는 접속 신청과 실제 요청이 나뉘어 있어서, 서버가 그사이 세션 번호를 붙잡고 있어야 했습니다. 새 규격에서는 요청 봉투(HTTP 헤더)에 "어떤 규격 버전인지, 어떤 도구를 부르는지"를 적어 보내고 본문에 입력값을 담아 한 번에 끝냅니다. 서버가 기억할 게 없으니 트래픽이 몰릴 때 서버를 여러 대로 늘리기도 수월해집니다.

### 5. 처음 보는 용어 풀이

- **모델 컨텍스트 프로토콜 (MCP, Model Context Protocol)** — AI 에이전트에게 새 도구를 붙여주는 표준 방식입니다. 2024년 11월 Anthropic이 처음 내놓았고, 도구 목록을 알려주고 실제로 실행시키는 절차가 정해져 있습니다.
- **상태를 기억하지 않는 방식 (stateless)** — 서버가 이전 요청을 전혀 기억하지 않고, 매 요청을 독립적으로 처리하는 설계입니다. 반대로 세션 번호처럼 뭔가를 기억해두는 방식을 상태 유지(stateful)라고 부릅니다.
- **세션 번호 (Mcp-Session-Id)** — 예전 방식에서 "지금 대화 중인 상대가 누구인지"를 표시하던 식별자입니다. 새 규격에서는 이게 필요 없어졌습니다.
- **명령줄 도구 (CLI, Command Line Interface)** — 화면의 버튼 대신 글자로 명령을 입력해 쓰는 프로그램입니다. 글쓴이가 만든 mcp-explorer가 이런 형태로, 서버에 어떤 도구가 있는지 목록을 뽑아보고 직접 하나 실행해볼 수 있습니다.
- **프롬프트 주입 공격 (prompt injection)** — 외부에서 읽어온 글에 몰래 지시문을 숨겨두어 AI가 엉뚱한 행동을 하게 만드는 공격입니다. 글쓴이는 예전에 MCP의 이 문제를 지적한 적이 있고, 지금은 터미널을 통째로 열어주는 쪽이 더 위험하다고 봅니다.
- **치명적 삼요소 (Lethal Trifecta)** — 글쓴이가 만든 표현으로, 민감한 데이터 접근·외부 콘텐츠 노출·외부로 내보낼 수 있는 통로가 한꺼번에 갖춰지면 데이터 유출 위험이 커진다는 문제의식을 가리킵니다.
- **Datasette** — 글쓴이가 만든, 데이터베이스를 웹으로 열어보게 해주는 도구입니다. 여기에 붙이는 datasette-mcp 플러그인은 데이터베이스 목록 보기·구조 보기·읽기 전용 조회 세 가지 기능만 AI에게 열어줍니다.

### 6. 한 발 더 들어가고 싶다면

- [2026-07-28 Model Context Protocol specification](https://modelcontextprotocol.io/) 형태로 원문이 가리키는 새 명세 — 요청 헤더와 본문이 실제로 어떻게 바뀌었는지 규격 자체를 확인할 수 있어요. (원문에서는 "the 2026-07-28 Model Context Protocol specification"으로 소개됩니다.)
- [May 21st blog post](https://simonwillison.net/2026/Jul/31/stateless-mcp/#atom-everything)에서 인용된 후보 규격(RC) 소개 글 — 예전 방식과 새 방식을 나란히 놓은 비교 예시가 실려 있어, 차이를 눈으로 보기 좋아요.
- [Model Context Protocol has prompt injection security problems](https://simonwillison.net/2026/Jul/31/stateless-mcp/#atom-everything)에서 언급된 글쓴이의 과거 글 — 도구를 자유롭게 조합해 쓸 때 생기는 보안 부담이 왜 사용자에게 떠넘겨지는지 짚어줍니다.
- [a shared Claude session](https://simonwillison.net/2026/Jul/31/stateless-mcp/#atom-everything)에 링크된 실제 대화 기록 — AI가 질문 하나에 답하려고 조회를 일곱 번 나눠 실행하는 과정을 직접 볼 수 있어요.
- [a new TIL](https://simonwillison.net/2026/Jul/31/stateless-mcp/#atom-everything)로 소개된 설정 메모 — 만들어둔 MCP 서버를 ChatGPT나 Claude에 실제로 연결하는 절차가 정리돼 있습니다.

# Stateless MCP이 다시 내 관심을 사로잡았다 (그리고 mcp-explorer와 datasette-mcp를 만들게 됐다)

2026년 7월 31일

화요일은 **Stateless MCP day**였다—MCP 2.0의 출시, 좀 더 격식 있지만 덜 기억하기 쉬운 이름으로 하자면 [2026-07-28 Model Context Protocol 스펙](링크)의 출시일이었다. 이는 MCP 스펙이 처음 출시된 이후 가장 중요한 변화이며, 이 프로토콜에 대한 내 개인적인 관심을 다시 불붙이는 계기가 되기도 했다.

배경 설명: MCP는 Model Context Protocol의 약자로, LLM 기반 에이전트 프레임워크에 새로운 도구를 노출시키는 표준 방식을 정의한다. 2024년 11월에 Anthropic이 처음 도입했고, 2025년 대부분의 기간 동안 엄청난 관심의 급증을 겪었다가, 이후 (역시 Anthropic이 발명한) Skills에 의해 다소 가려졌다—터미널과 curl에 접근할 수 있는 에이전트 하네스가 MCP가 하던 대부분의 일을 더 유연한 방식으로 할 수 있다는 게 명확해지면서였다. 나는 이에 대해 내 2025년 리뷰에서 쓴 바 있다.

나는 지금 MCP로 다시 돌아오고 있다. 에이전트에게 인터넷에 접근할 수 있는 셸 환경을 주는 것은 위험으로 가득 차 있고, 그런 환경을 효과적으로 운용할 수 있는 강력한 모델을 필요로 한다. MCP 도구는 감사하고 통제하기가 더 쉽고, 노트북에서 돌아가는 더 작은 모델도 이를 그럭저럭 잘 운용할 수 있을 만큼 충분히 단순하다.

새로운 stateless MCP 스펙은 이 프로토콜의 클라이언트와 서버를 구현하는 복잡성 또한 크게 줄여준다. 나는 이번 주에 그런 것을 세 가지나 만들었다!

## Stateless MCP으로 더 쉬워진 것

stateful MCP와 stateless MCP의 차이를 가장 잘 보여주는 예시는 새 스펙의 RC를 소개했던 [5월 21일 블로그 포스트](링크)에 있다. 그 글에는 명확한 전후 비교 예시가 포함되어 있었다.

기존의 stateful MCP(나는 이를 "레거시 MCP"라고 부르겠다)는 두 번의 HTTP 요청을 필요로 했다—첫 번째는 세션을 초기화하고 `Mcp-Session-Id`를 획득하는 요청, 두 번째는 실제로 도구를 호출하는 요청이었다:

```
POST /mcp HTTP/1.1
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
    },
    "clientInfo": {
      "name": "my-app",
      "version": "1.0"
    }
  }
}

POST /mcp HTTP/1.1
Mcp-Session-Id: 1868a90c-3a3f-4f5b
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": {
      "q": "otters"
    }
  }
}
```

새로운 stateless 방식은 다음과 같이 생긴 단일 HTTP 요청을 사용한다:

```
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": {
      "q": "otters"
    },
    "_meta": {
      "io.modelcontextprotocol/clientInfo": {
        "name": "my-app",
        "version": "1.0"
      }
    }
  }
}
```

이는 클라이언트 측 구현이든 서버 측 구현이든 훨씬 더 깔끔하다. 또한 확장 가능한 웹 애플리케이션을 구축하는 데도 더 적합한데, 이제는 그 세션 ID를 추적하기 위한 서버 측 상태를 유지할 필요도 없고, 같은 세션을 같은 백엔드 머신으로 라우팅하는 것을 걱정할 필요도 없기 때문이다.

## mcp-explorer

MCP 서버를 대화형으로 탐색해볼 만한 괜찮은 CLI 도구를 찾을 수 없어서, Codex에게 도움을 받아 직접 만들었다. **mcp-explorer**가 그 결과물이다. 이것은 stateless한 Python CLI 도구라서, 시험해보기 위해 설치할 필요조차 없다—`uvx`로 다음과 같이 쓸 수 있다:

```
uvx mcp-explorer list https://agentic-mermaid.dev/mcp
```

이는 Ade Oshineye의 `agentic-mermaid.dev` 데모 MCP를 조회한다. 위 명령은 다음과 같은 도구 목록을 반환한다:

```
execute(code: string, timeoutMs?: integer) - Execute Mermaid SDK code
  Run JavaScript in an isolated sandbox; return a value.

describe_sdk(family: string, detail?: string) - Describe Mermaid SDK operations
  Return version-matched mutation operations for one diagram family.

render_svg(source: string, options?: object) - Render Mermaid as SVG
  Render a Mermaid source string to themeable SVG. Returns { ok, svg }.

render_ascii(source: string, useAscii?: boolean, targetWidth?: integer, options?: object) - Render Mermaid as text
  Render a Mermaid source string to text. Returns { ok, text }.

render_png(source: string, scale?: number, background?: string, fitTo?: object, options?: object) - Render Mermaid as PNG
  Rasterize a Mermaid source string to PNG. Returns { ok, png_base64 }.
...
```

그런 다음 어떤 도구 하나를 살펴보려면:

```
uvx mcp-explorer inspect render_svg
```

이는 입력과 출력의 JSON 스키마를 포함한 상당한 양의 정보를 출력해준다.

그 도구를 호출하고 인자를 넘기려면:

```
uvx mcp-explorer call \
  https://agentic-mermaid.dev/mcp \
  render_svg \
  -a source '
graph TD; A-->B
' \
  -a options '
{"padding":24}
'
```

이는 다음을 반환한다:

```
{"ok":true,"svg":"<svg xmlns=\"http://www.w3.org/2000/svg\" width=...
```

순수한 SVG만 얻으려면 그 명령 뒤에 `| jq .svg -r`를 추가하면 된다. 나는 이 이미지를 받았다(this image).

README에는 몇 가지 명령이 더 있다(a few more commands). 하지만 대략적인 감은 잡았을 것이다. 나는 이런 식의 CLI 도구를 만드는 것이, 실제 코드 대부분을 에이전트가 작성한다 해도, 스펙에 익숙해지는 매우 생산적인 방법이라고 생각한다.

## datasette-mcp

두 번째 프로젝트는 **datasette-mcp**로, 어떤 Datasette 인스턴스에든 `/-/mcp` 엔드포인트를 추가해주는 Datasette 플러그인이다.

이 플러그인을 만들려고 시도한 건 아마 이번이 네 번째일 텐데, 새로운 stateless MCP 스펙 덕분에 마침내 릴리스할 만하다고 느껴지는 버전을 갖게 됐다.

이 플러그인은 딱 세 가지 도구를 제공한다: `list_databases()`, `get_database_schema(database_name)`, 그리고 `execute_sql(database_name, sql)`. 이들은 정확히 예상한 대로 동작한다—다만 `execute_sql()`은 현재로서는 읽기 전용이다.

이것들을 에이전트나 ChatGPT, Claude 같은 챗 도구에 연결하면, 이들은 여러분이 호스팅하는 Datasette 인스턴스에 대해 SQL 쿼리를 실행할 수 있는 능력을 갖게 된다.

지금까지는 내 블로그의 Datasette 미러인 `datasette.simonwillison.net/-/mcp`에서 이를 돌리고 있다. 이를 ChatGPT와 Claude에 연결하는 방법을 알아내는 데 약간의 시행착오가 필요했지만, 결국 해냈다. 정확히 그 방법을 보여주는 새 TIL(a new TIL)이 여기 있다.

여기 공유된 Claude 세션(a shared Claude session)이 있는데, 거기서 나는 이렇게 물었다:

> list tables in simonwillison.net

그리고 이어서:

> what has Simon said recently about MCP?

이 질문에 답을 알아내기 위해 이 세션은 7개의 개별 SQL 쿼리를 실행했다.

## llm-mcp-client

내 LLM 도구는 공식적인 MCP 통합을 오래전부터 필요로 했다. 새로운 알파 버전 **llm-mcp-client** 플러그인이 바로 그것을 위한 나의 시도다:

```
llm install llm-mcp-client
llm -T 'MCP("https://datasette.simonwillison.net/-/mcp")' 'count the notes'
```

다음은 그 출력이다(추론 과정 포함, 나는 LLM 0.32rc2를 사용하고 있다):

> Considering note count
> I see the question "count the notes" is probably asking me to tally up blog notes. It could also mean published notes or drafts, so there's some ambiguity there. ## MCP는 에이전트로 구축하는 더 안전한 방법이다

MCP가 처음 출시되고 몇 달 후, 나는 "Model Context Protocol has prompt injection security problems"라는 글을 썼는데, 거기서 최종 사용자가 도구들을 자유롭게 조합하는 패턴이 데이터 유출 공격을 피해야 할 책임을 사용자 자신에게 떠넘긴다는 점을 지적했다. 그때는 아직 "the Lethal Trifecta"라는 용어를 만들어내지 않았지만, 내가 염두에 두었던 것은 바로 그것이었다.

그 후 임의의 셸과 curl 접근 권한을 가진 범용 에이전트들이 등장했고, 그것들은 보안을 유지하기가 훨씬 더 어렵다!

내가 MCP에 대해 높이 평가하게 된 점은, 오늘날 대부분의 범용 및 코딩 에이전트 도구들의 기본값인 개방된 네트워크 환경에서의 임의 명령 실행보다, 에이전트의 능력과 무엇이 잘못될 수 있는지를 훨씬 더 쉽게 추론할 수 있다는 것이다.

민감한 애플리케이션을 LLM 위에 구축할 때는 MCP를 앞으로 훨씬 더 많이 활용할 계획이다.
