## 📌 학습 정리

### 1. 한 줄로 말하면

큰일을 맡기면 Claude가 "몇 명을, 어떤 순서로, 무슨 일에 붙일지"를 스스로 짜서 여러 Claude에게 나눠 맡기는 기능이에요. 사람은 그 조직도를 직접 그리지 않아도 됩니다.

### 2. 왜 이게 만들어졌어요?

원래 Anthropic의 Claude Managed Agents(개발자가 API로 Claude 에이전트를 만들어 돌리는 서비스)에서 여러 에이전트를 함께 쓰려면, 개발자가 직접 판을 짜야 했어요. 전체를 지휘할 조정자(coordinator)를 하나 정하고, 그 아래서 일할 하위 에이전트(sub-agent) 명단(roster)을 미리 구성하는 식이었죠. 그런데 에이전트가 많아질수록 사람이 오히려 병목(bottleneck)이 됩니다. 발표자 CJ Avilla는 에이전트들이 코드 변경 요청(PR, Pull Request)을 엄청나게 올리는데 사람은 GitHub 앞에 앉아 하나하나 승인하면서 "내가 제일 먼저 무너지겠구나" 싶어진다고 했어요. 그래서 일을 나누고 연결하는 부분까지 Claude에게 넘기자는 게 동적 워크플로(dynamic workflows), 발표자들이 줄여서 "플로(flows)"라고 부른 기능입니다.

### 3. 비유로 풀면

리눅스(Linux) 개발 방식과 비슷해요. 처음엔 리누스 토르발스 한 사람이 만들었지만, 프로젝트가 커지면서 믿고 맡길 수 있는 관리자들이 층층이 생겼죠. 발표자들도 이 이야기를 꺼내면서, 에이전트도 큰 프로젝트를 하려면 이 정도로 조직을 갖춰야 한다고 설명했어요.

조금 더 일상적으로 보면 프로젝트 리더 같은 거예요. 리더가 일을 받으면 먼저 계획을 세우고, 팀원 몇 명에게 어떤 일을 나눌지 정하고, 다 끝나면 결과를 모아 검토하잖아요. 이때 팀원끼리 직접 메신저를 주고받지는 않고 공용 폴더에 결과물을 올려 두고 공유한다고 생각하면 됩니다.

그래서 결국, 지금까지는 사람이 짜 주던 팀 구성과 업무 분배를 이제 리더 역할의 Claude가 직접 설계한다는 거예요.

### 4. 어떻게 작동하는지 (그림으로)

```mermaid
flowchart TD
    A[사람이 큰 작업을 맡김<br/>세션 예산도 함께 설정] --> B[리드 에이전트가<br/>작업 계획을 세움]
    B --> C[리드 에이전트가<br/>조율용 프로그램을 직접 작성]
    C --> D1[하위 에이전트 1<br/>종목 A 조사<br/>독립된 작업 공간]
    C --> D2[하위 에이전트 2<br/>종목 B 조사<br/>독립된 작업 공간]
    C --> D3[하위 에이전트 3<br/>종목 C 조사<br/>독립된 작업 공간]
    D1 --> E[(함께 쓰는 파일 공간)]
    D2 --> E
    D3 --> E
    E --> F[검토 단계<br/>조사 결과를 모아 점검]
    F --> G[최종 보고서]
    C -.-> H[Claude Console 그래프 화면<br/>누가 누구에게 무엇을 넘겼는지 확인]
```

먼저 리드 에이전트(lead agent)가 일을 어떻게 끝낼지 계획을 세우고, 에이전트를 띄우고 결과를 모으고 정보 흐름을 관리하는 조율 프로그램을 직접 작성해요. 발표에서 보여 준 주식 관심 종목 스캐너 예시에서는, 조사 단계에서 종목 하나하나를 서로 맥락이 섞이지 않는 에이전트들에게 나눠 주고, 그다음 검토 단계에서 결과를 살펴본 뒤 보고서를 만들었습니다. 에이전트끼리 API로 직접 메시지를 보내라고 지시할 수는 없고, 대신 파일 공간을 함께 써서 정보를 주고받아요. 리드가 하위 에이전트에게 무엇을 넘겼는지는 Claude Console의 그래프 화면에서 단계마다 들여다볼 수 있다고 합니다.

### 5. 처음 보는 용어 풀이

- **여러 에이전트 조율 (multi-agent orchestration)** — AI 에이전트 여러 개에게 일을 나눠 주고 결과를 모으는 방식이에요. 플로는 이 조율 방식의 다음 버전으로 소개됐고, 가장 큰 차이는 팀 구성을 Claude가 정한다는 점이에요.
- **리드 에이전트 / 하위 에이전트 (lead agent / sub-agent)** — 리드는 계획을 세우고 일을 나누는 지휘자, 하위 에이전트는 나눠 받은 일을 하는 팀원이에요. 원하면 개발자가 특정 분야를 맡을 하위 에이전트를 미리 설정해서 넣어 줄 수도 있어요.
- **독립된 맥락 (isolated context)** — 하위 에이전트마다 자기만의 작업 공간이 따로 있다는 뜻이에요. 다른 종목 이야기가 섞이지 않아서 한 가지 일에만 집중할 수 있어요.
- **세션 예산 (session budget)** — 한 번 실행할 때 쓸 수 있는 비용 상한이에요. 모델은 실행 중에 자기 예산을 모르고, 개발자가 바깥에서 정해 둡니다. 발표자는 모델에게 예산을 알려 주면 에이전트가 "살짝 불안해할" 수도 있다고 농담처럼 말했어요.
- **드리밍 (dreaming)** — 아직 미리 써 보는 단계(research preview)에 있는 기능이에요. 기존 기억 저장소와 지난 작업 기록을 함께 읽고, 중복은 합치고 낡았거나 서로 어긋나는 내용은 바꾸고 새로 얻은 깨달음은 드러내서 정리된 기억 저장소를 새로 만들어요. 같은 플로를 반복해서 돌릴 때 점점 더 싸고 효율적으로 만드는 방법으로 언급됐어요.
- **평가 (evals)** — 결과가 잘 나오는지 체계적으로 시험해 보는 과정이에요. "간단한 일에 에이전트를 수백 개 띄우면 어떡하냐"는 질문에 발표자는 평가를 하고 기본값을 낮게 잡아 두는 게 답이라고 했어요.
- **테스트 시점 연산 (test-time compute)** — 모델을 다 만든 뒤 실제로 문제를 풀 때 계산을 더 많이 쓰는 것을 말해요. 발표자는 플로를 "어려운 문제에 계산을 더 쏟아부어 모델에서 더 큰 능력을 더 빨리 끌어내는 방법"이라고 설명했어요.

한 가지 짚어 두면, 관심 종목 스캐너 비교에서 플로는 에이전트 하나로 처리할 때보다 비용이 "훨씬 더" 들었지만 세부 내용을 빠짐없이 찾아내는 데는 "훨씬 더 효과적"이었다고 해요. 그래서 예산을 정해 두는 게 중요하다는 이야기가 함께 나왔습니다.

Avilla는 이렇게 말했다. "지금 많은 에이전트를 오케스트레이션하고 관리하는 우리 중 상당수는, 에이전트들이 엄청나게 많은 PR을 올리는 상황에서 **자신이 병목이자 한계점이 되어 간다는 느낌**을 받기 시작했을 겁니다. 우리는 GitHub 앞에 앉아 PR을 승인하고, 모든 것이 예상대로 동작하는지 확인하고 있죠."

두 사람은 dynamic workflows가 Claude Code에서 "모든 작업을 위한 하네스(a harness for every task)"라는 개념으로 시작되었다고 밝혔다. 하지만 **flows는 단일 에이전트나 고정된 로스터(roster)보다 더 오래 실행될 수 있다.** 기본 아이디어는 Claude가 에이전트들의 조직 구성을 직접 선택한다는 것이다.

Stall은 이렇게 말했다. **"Flows는 본질적으로 멀티에이전트 오케스트레이션의 차세대 버전입니다.** Claude가 자신의 멀티에이전트 토폴로지 전체를 완전히 직접 오케스트레이션하도록 맡길 수 있는 거죠."

작동 방식은 다음과 같다. 리드 에이전트가 작업을 어떻게 달성할지에 대한 계획을 세운다. 그러면 Claude는 에이전트를 실행하고, 결과를 수집하며, 정보 흐름을 관리하는 오케스트레이션 프로그램을 작성한다.

이전의 Claude Managed Agents에서는 개발자가 코디네이터와 서브에이전트 로스터를 직접 구성해야 했다. **Dynamic workflows에서는 작업을 어떻게 나누고 조율할지를 Claude 스스로 결정한다.**

Stall은 이렇게 말했다. "멀티에이전트 오케스트레이션의 여러 단계에 걸쳐, 그것들 사이의 연결을 사용자가 전혀 관리하지 않아도 개별적이고 검증 가능한 작업 단위를 완수할 수 있습니다."

[![이미지 3](https://substackcdn.com/image/fetch/$s_!cNfD!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F2ec1518b-8dad-41f1-b3c8-f453f3752cec_1260x1190.png)](https://substackcdn.com/image/fetch/$s_!cNfD!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F2ec1518b-8dad-41f1-b3c8-f453f3752cec_1260x1190.png)

다만 Avilla는 **사용자가 원한다면 전문 서브에이전트를 도입할 수 있다**고 덧붙였다.

그는 "에이전트 설정(agent config)에서 사전 구성된 서브에이전트를 전달하는 것도 가능합니다"라고 말했다.

이 모든 기능은 API를 통해 Claude에 접근하는 개발자들이 사용하는 인터페이스인 **Claude Console**에서 이용할 수 있으며, 이는 Claude Managed Agents의 핵심 취지이기도 하다.

[![이미지 4](https://substackcdn.com/image/fetch/$s_!rDfm!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fd16fc0e8-d7a4-4b1b-b6e9-7cd0e95cc34a_2048x1124.png)](https://substackcdn.com/image/fetch/$s_!rDfm!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fd16fc0e8-d7a4-4b1b-b6e9-7cd0e95cc34a_2048x1124.png)

_Managed Agents가 위치한 Claude Console._

이어서 발표자들은 주식 관심종목(watchlist) 스캐너라는 비교적 단순한 워크플로우를 보여 주었다. Anthropic이 장려하는 크고 야심 찬 프로젝트와는 거리가 멀었지만, **기본 패턴**을 보여 주기에는 충분했다. 스캔 단계에서는 **개별 티커를 격리된 컨텍스트를 가진 에이전트들에게 분배**했고, 이후의 리뷰 단계에서는 결과를 검토한 뒤 리포트를 작성했다.

청중 Q&A에서는 여러 잠재적 문제가 제기되었다. 한 청중은 **Claude가 한 작업에 에이전트가 몇 개 필요한지 어떻게 결정하는지**, 그리고 단순한 티커 스캔이 수백 개의 서브에이전트를 촉발할 수도 있는지 물었다.

Stall은 "답은 사실 **evals와 낮은 기본값**입니다"라고 답하며, 야심 찬 작업은 대체로 더 큰 병렬화를 명시적으로 유도해야 한다고 언급했다.

에이전트 오케스트레이션의 오랜 우려 중 하나는 **토큰 예산에 대한 통제권을 유지하는 것**이다. 누군가 리드 에이전트가 자신에게 쓸 수 있는 돈이 얼마인지 아느냐고 물었다.

Stall은 모델이 실행 중에는 자신의 예산을 알지 못하지만, 개발자가 세션 예산을 설정할 수 있다고 답했다. 그는 **모델에게 예산을 알려 주면 에이전트가 "약간 불안해질" 수 있다**고 덧붙였고, 청중석에서는 웃음이 터졌다.

[![이미지 5](https://substackcdn.com/image/fetch/$s_!RJ39!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Ff79ff38b-6346-410b-9257-28bdc64bd868_1438x1064.png)](https://substackcdn.com/image/fetch/$s_!RJ39!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Ff79ff38b-6346-410b-9257-28bdc64bd868_1438x1064.png)

주식 관심종목 예시의 스캐너.

관련된 질문으로, 개발자가 **반복 실행되는 flows를 시간이 지날수록 더 저렴하고 효율적으로** 만들려면 어떻게 해야 하는지도 나왔다.

Claude에게 발생한 비용을 검토해 달라고 요청하는 방법 외에, Avilla는 비교적 새로운 또 다른 기능인 **dreaming**을 쓸 것을 제안했다. [문서](https://platform.claude.com/docs/en/managed-agents/dreams)에서 "dreaming"은 리서치 프리뷰(research preview) 기능으로 정의된다. dream은 "기존 메모리 스토어를 과거 세션 트랜스크립트와 함께 읽은 뒤, **새롭게 재구성된 메모리 스토어를 생성**"하며, 중복 항목은 병합하고 "오래되었거나 모순되는 항목"은 교체하며 "새로운 인사이트를 도출"한다.

Avilla는 flow 맥락에서의 dreaming을 해당 세션들과 관련된 **"메모리 스토어를 결정화(crystallize)하고 기본적으로 개선할 수 있는"** 것이라고 설명했다.

주식 관심종목 예시와 관련해, 누군가 **관심종목 flow가 스스로 개선될 수 있는지** 물었다. 예를 들어 자신의 스캔 모델이 부적절하다는 것을 인식하고 다음 예약 실행을 바꿀 수 있는가 하는 질문이었다.

Stall은 이것이 내장된 기능은 아니라고 답했고, 그와 Avilla는 **힐 클라이밍(hill-climbing)과 dreaming**을 활용해 이 루프를 개선할 수 있다고 제안했다.

[![이미지 6](https://substackcdn.com/image/fetch/$s_!-s5o!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F6e94b828-cc7d-418d-83cf-4f1b555aeddc_1474x1116.png)](https://substackcdn.com/image/fetch/$s_!-s5o!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F6e94b828-cc7d-418d-83cf-4f1b555aeddc_1474x1116.png)

Managed Agents의 brain/hands 개념 개요.

또 다른 청중은 **서브에이전트의 행동에 대한 가시성**은 어떠냐고 물었다.

Avilla는 개발자가 Claude Console 내부의 그래프 기능을 통해 언제든 이를 확인할 수 있다고 답했다.

**"리드 에이전트가 서브에이전트에게 실제로 무엇을 넘겼는지** 알 수 있습니다. 여기서 그 페이로드를 보면, 이 그래프 전체의 모든 전환(transition)에서 실제로 무슨 일이 일어나는지 깊이 이해할 수 있습니다."

또 다른 흥미로운 질문은 **서브에이전트들끼리 서로 통신할 수 있는지**였다.

Stall은 **에이전트들이 파일시스템을 공유**하며 이를 통해 정보를 주고받을 수 있지만, 개발자가 API를 통해 한 워크플로우 서브에이전트에게 다른 서브에이전트로 메시지를 보내도록 직접 지시할 수는 없다고 말했다.

관심종목 스캐너 비교에서 Avilla는 flows가 단일 에이전트 방식보다 "훨씬 더" 비용이 들지만, **"모든 세부 사항을 찾아내는 데는 훨씬 더 효과적"**이라고 말했다.

[![이미지 7](https://substackcdn.com/image/fetch/$s_!fJVm!,w_1456,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F08c9072d-bef4-4262-a582-974384824502_1494x1114.png)](https://substackcdn.com/image/fetch/$s_!fJVm!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F08c9072d-bef4-4262-a582-974384824502_1494x1114.png)

예산 설정이 핵심입니다!

더 큰 질문은 **flows가 실제로 얼마나 야심 찰 수 있는가**였다. 한 청중은 OpenAI가 최근 발표한 **Navier–Stokes 밀레니엄 문제(Millennium Prize problem)** 증명을 언급하며, dynamic workflows가 대규모 과학 연구 프로젝트를 구동할 수 있는지 물었다.

Stall은 Anthropic이 대규모 과학 문제를 어떻게 계산하는지에 대한 구체적인 내용은 밝히지 않았지만, **일반 사용자도 그러한 문제에 도전할 수 있게 하는 것이 그들의 목표**라고 말했다.

그는 "Flows는 기본적으로 **어려운 문제에 테스트 타임 컴퓨트(test-time compute)를 투입**해 모델에서 더 많은 역량을 더 빠르게 끌어내는 방법입니다"라고 말했다. "특히 API 서비스로서, 이것의 힘을 열어 주는 것이 이런 종류의 발견이나 과학적 진전을 **일반 대중이 폭넓게 해낼 수 있게** 만드는 첫걸음이라고 생각합니다."
