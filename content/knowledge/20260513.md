사람과 인공지능이 서로 말을 끊고, 동시에 보고 들으면서 자연스럽게 대화할 수 있도록 처음부터 새로 설계된 음성·영상 모델이 등장했어요. 기존처럼 "내가 말하면 → AI가 듣고 → AI가 답하는" 순서가 아니라, 사람끼리 대화하듯 동시에 진행됩니다.

### 2. 왜 이게 만들어졌어요?

지금까지 음성 AI는 보통 세 단계 파이프라인으로 만들어졌어요. 사람의 말을 글자로 받아쓰는 단계(STT), 그걸 글로 답하는 거대 언어 모델(LLM), 답을 다시 음성으로 바꾸는 단계(TTS)를 이어 붙인 구조죠. 이 구조는 "한 사람이 말을 끝내야 다음 사람이 말한다"는 턴 기반(turn-based) 가정 위에 서 있어서, 말을 끊거나, 듣는 동시에 반응하거나, 화면을 보면서 실시간으로 코멘트하는 일이 어색했어요. 그래서 Thinking Machines 팀은 음성·영상·텍스트를 동시에 입출력하는 능력을 모델 자체의 기본 능력으로 처음부터 학습시키는 방향을 택했습니다. 발표 글에서도 이걸 "사람과 AI 사이의 대역폭(bandwidth) 문제"라고 표현하고 있어요 — 정보를 주고받는 통로가 좁아서, 모델이 듣기·말하기·보기·생각하기·검색하기를 한꺼번에 해내야 한다는 뜻입니다.

### 3. 비유로 풀면

이건 마치 **무전기(walkie-talkie) 대화에서 일반 전화 통화로 넘어가는 변화**와 비슷해요. 무전기는 "오버"라고 말해야 상대가 말할 차례가 되지만, 전화는 두 사람이 동시에 말하고, 끊고, 맞장구치고, 침묵으로 답할 수도 있죠. 또 다른 비유로는 **운전 강사 옆자리**예요. 강사는 학생이 운전하는 모습을 계속 지켜보다가 필요한 순간에 "지금 깜빡이!"라고 알아서 말을 꺼내잖아요. 누가 물어볼 때까지 기다리는 게 아니라요.

그래서 결국, 이 모델은 "질문 받고 답하는 비서"가 아니라 "곁에서 같이 보고 들으면서 알아서 끼어드는 동료"에 가깝게 작동합니다.

### 4. 어떻게 작동하는지 (그림으로)

```mermaid
flowchart LR
    A[사람의 말소리·영상·텍스트<br/>끊기지 않고 계속 들어옴] --> B[200ms 단위의<br/>아주 짧은 조각으로 쪼갬<br/>'마이크로턴']
    B --> C[하나의 모델이<br/>듣기·보기·생각하기·말하기를<br/>동시에 처리]
    C --> D[필요한 순간에 직접<br/>말을 꺼내거나 침묵하거나<br/>도구를 호출]
    D -.피드백.-> A
```

핵심은 입력과 출력을 200밀리초(0.2초) 정도의 아주 짧은 조각으로 끊어서 시간 축에 나란히 정렬한다는 점이에요. 모델은 매 조각마다 "지금 말할까, 들을까, 그냥 가만히 있을까, 검색할까"를 스스로 정합니다. 그래서 "지금부터 4초마다 호흡 알려줘"처럼 시간 자체를 다루는 지시도, "내가 다른 언어 섞어 쓰면 원래 단어 알려줘"처럼 사용자의 흐름을 가로채야 하는 지시도 자연스럽게 처리할 수 있다고 해요.

### 5. 처음 보는 용어 풀이

- **네이티브 인터랙션 모델 (native interaction model)** — 음성 인식·언어 모델·음성 합성을 따로 붙이지 않고, 처음부터 실시간 상호작용 능력 자체를 학습한 모델이에요. "기능을 덧댄" 게 아니라 "처음부터 그렇게 태어난" 모델이라는 뜻입니다.
- **음성 활동 감지, VAD (Voice Activity Detection)** — 마이크 입력 중 어디가 사람의 말이고 어디가 침묵인지 잘라주는 기존 보조 모듈이에요. 턴을 나누는 기준이 됐는데, 이번 모델은 시간 단위로 잘게 쪼갠 흐름 위에서 동작하기 때문에 이런 별도 모듈이 필요 없다고 합니다.
- **마이크로턴 (microturn)** — 한 사람의 발화 한 덩어리(턴)를 200밀리초처럼 아주 짧은 조각으로 쪼갠 단위예요. 이렇게 쪼개면 말하면서 듣고, 듣다가 끼어드는 동작을 모델이 자연스럽게 표현할 수 있어요.
- **인코더 없는 조기 융합 (encoder-free early fusion)** — 이미지·오디오·텍스트를 각자 따로 처리한 뒤 합치는 게 아니라, 처음부터 같은 모델 안에 함께 흘려보내는 방식이에요. 모달리티마다 별도 변환기(encoder)를 두지 않아 지연이 적습니다. Meta의 Chameleon 모델이 같은 계열이에요.
- **전문가 혼합, MoE (Mixture of Experts)** — 모델 안에 여러 명의 "전문가" 부분망을 두고, 입력마다 일부만 활성화해서 쓰는 구조예요. 이번 모델은 전체 2,760억 파라미터 중 매번 120억만 사용한다고 해서 "276B-A12B"라고 표기됩니다.
- **시각적 능동성 (visual proactivity)** — 사용자가 묻기 전에 화면이나 카메라 영상을 보고 모델이 먼저 입을 여는 능력이에요. 예: "자세 구부정해지면 알려줘", "팔굽혀펴기 횟수 세줘". 기존 음성 AI가 잘 못하던 부분이라고 짚고 있어요.
- **풀 듀플렉스 (full-duplex)** — 양쪽이 동시에 말하고 들을 수 있는 통신 방식이에요. 일반 전화가 풀 듀플렉스, 무전기가 반(half) 듀플렉스죠. 음성 AI 맥락에서는 "AI가 말하는 도중에도 사용자 말을 듣고 반응할 수 있다"는 뜻입니다.

공식 블로그 포스트에는 연속적인 상호작용의 수준을 보여주는 많은 데모가 포함되어 있으며, 각각 200ms 단위의 "시간 정렬 마이크로턴(time-aligned microturn)" 스트림에 초점을 맞추고 있습니다:

Meta의 Chameleon과 유사하게, 인코더 없는 조기 융합(encoder-free early fusion)을 사용하여 이미지와 오디오를 모두 200ms 이내에 처리합니다:

팀이 공개한 다수의 공식 벤치마크에서는 BigBench Audio, IFEval, FD-bench 같은 기본 항목들에서 **GPT-Realtime-2**와 **Gemini 3.1-Flash** 모두를 능가하는 결과를 보여줍니다. 그러나 목표로 하는 상호작용 수준을 측정하기 위해 시간 인식, 동시 번역, 시각적 능동성(visual proactivity)을 위한 2개의 새로운 내부 벤치마크를 만들어야 했습니다:

- **TimeSpeak**: 모델이 사용자가 지정한 시간에 말을 시작할 수 있는가?
  - 예시: "호흡 연습을 하고 싶어. 내가 멈추라고 할 때까지 4초마다 숨을 들이쉬고 내쉬라고 알려줘."
- **CueSpeak**: 모델이 적절한 순간에 말할 수 있는가?
  - 예시: "내가 코드 스위칭(codeswitching)을 해서 다른 언어를 쓸 때마다, 원래 언어로 올바른 단어를 알려줘."
- **RepCount-A**: 반복 동작이 담긴 영상을 온라인 카운팅 작업으로 변환한 것으로, 연속적인 시각 추적 및 적시 카운팅을 측정합니다.
- **ProactiveVideoQA**: 특정 순간에 답을 알 수 있는 질문이 포함된 영상으로 구성됩니다. 높은 점수를 받으려면 정확한 시간에 정확한 답을 해야 하며, 침묵은 부분 점수를 얻고 오답은 감점됩니다.
- **Charades**: 표준 시간적 행동 위치 파악(temporal action-localization) 벤치마크입니다.
  - 사용자 오디오 지시 스트리밍: "사람이 {action}을 시작하면 'start'라고 말하고, 멈추면 'stop'이라고 말해줘."

그러나 숫자를 넘어서 살펴보세요: 가장 visceral(생생)한 데모는 맨 아래에 묻혀 있는 이것입니다. 샘플을 재생하고 AGI를 체감해 보세요.

### 에이전트 하네스(Harness), 로컬 우선 툴링, 제어 표면

**더 나은 에이전트 제어 플레인이 하나의 제품 카테고리가 되고 있다**: 반복되는 불만은 유용한 에이전트에는 자율성이 필요하지만 엔지니어들은 여전히 되돌릴 수 있고 검사 가능한 제어를 원한다는 것입니다. `@itsclelia`는 이에 대해 **aggit**으로 대응했습니다. 이는 에이전트 아티팩트의 로컬/원격, S3 기반 스토리지를 위한 Rust CLI로, 메인 Git 히스토리 외부에서 stash/branch/restore 시맨틱스를 가능하게 합니다. 같은 맥락에서 `@_catwu`는 여러 Claude Code 에이전트를 관리하기 위한 새로운 **claude agents** 터미널 제어 플레인을 소개했으며, `@cursor_ai`는 Cursor를 **Microsoft Teams**에 도입하여 에이전트가 전체 스레드를 읽고 PR을 열 수 있게 했습니다. 이 모두는 "에이전트 오케스트레이션"이 프롬프트 트릭만이 아니라 구체적인 UX 패턴으로 수렴하고 있다는 신호입니다.

**Deep Agents / Hermes / 로컬 에이전트가 빠르게 성숙하고 있다**: `@masondrxy`는 **Deep Agents CLI**가 컨텍스트를 잃지 않고 **대화 중간에 기반 모델 공급자를 핫 스왑**할 수 있다고 언급했습니다. 이는 많은 에이전트 스택이 여전히 놓치고 있는 비자명한 시스템 기능입니다. LangChain도 공급자/모델별 튜닝을 위한 **harness profiles**를 소개했으며(트윗), 같은 저자의 별도 가격 분석에 따르면 **DeepSeek V4 Flash**는 고용량 에이전트 워크로드에서 GPT/Gemini flash 티어 옵션보다 극적으로 저렴할 수 있습니다(트윗). 로컬 측에서는 Hugging Face가 **로컬 앱에 Hermes Agent 지원 및 네이티브 트레이스 시각화**를 추가했으며, `@Teknium`은 로컬/오픈 모델뿐만 아니라 프론티어 API도 명시적으로 타겟팅하는 Hermes Agent와 CUA를 통한 **모든 모델로의 컴퓨터 사용**을 미리 보여줬습니다. `@onusoz`가 Hugging Face에 합류하여 **OpenClaw** 및 관련 오픈 하네스의 로컬 모델을 개선하는 것도 로컬 에이전트 인체공학이 이제 전략적 인프라가 되었다는 강력한 신호입니다.

**도구에 대한 디자인 테제가 등장하고 있다**: `@threepointone`은 에이전트가 점근적으로 단 **두 가지 원시 도구: 검색과 실행**만을 원하게 될 수 있으며, 계속 확장되는 정적 도구 메뉴 대신 기능의 동적 의미론적 발견이 이루어질 것이라고 주장했습니다. 이는 거대한 모놀리식 프롬프트 대신 구성 가능한 하네스로의 광범위한 이동을 보완합니다.

### 벤치마크, 효율성 및 오픈 모델 경제학

**코딩 에이전트 벤치마킹이 마침내 하네스+모델 쌍을 측정하고 있다**: **Artificial Analysis가 Coding Agent Index를 출시**했습니다. SWE-Bench-Pro-Hard-AA, Terminal-Bench v2, SWE-Atlas-QnA를 포괄하며, 모델만이 아니라 **모델+하네스 조합**을 비교합니다. 최상위 결과: Cursor CLI에서 **Opus 4.7**이 **61점**을 기록했으며, Codex/Claude Code에서 **GPT-5.5**가 바로 뒤를 이었습니다. 상위 오픈 웨이트 설정에는 Claude Code에서 **GLM-5.1**, **Kimi K2.6**, **DeepSeek V4 Pro**가 포함되었으며, 경쟁력은 있지만 의미 있는 격차로 뒤처졌습니다. 이 벤치마크는 또한 **작업당 비용**(>30배), **토큰 사용량**(>3배), **캐시 적중률**(80–96%), **작업당 시간**(>7배)에서 큰 변동을 드러냈습니다. 해당 벤치마크는 OpenHands의 업데이트된 소프트웨어 엔지니어링 벤치마크 발표(트윗)와, 오피스·금융·터미널·웹 작업에 걸쳐 더 에이전틱한 작업 믹스를 가진 Claw-Eval로 보완되었으며, 여기서 **MiMo-V2.5-Pro가 선두**를 달리고 **DeepSeek V4 Flash가 크기 대비 비정상적으로 효율적**으로 보였습니다.

**TurboQuant에 대한 회의론이 증가하고 있다**: 여러 포스트가 최근 인기를 끈 양자화/서빙 기법에 대한 더 냉철한 시각을 지적했습니다. `@_EldarKurtic`은 정확도, 레이턴시, 처리량을 다루는 **TurboQuant**에 대한 첫 번째 포괄적 연구라고 묘사한 것을 발표했으며, `@vllm_project`는 Red Hat / vLLM 조사를 출발점으로 링크했고, `@jbhuang0604`은 결론을 "실제로 잘 작동하지 않는다"고 직설적으로 요약했습니다. 이것은 독립적인 재현이 중요한 인프라 주장의 전형적인 사례입니다.

**로컬/오픈 모델이 하드웨어 한계보다 빠르게 개선되고 있다**: `@ClementDelangue`가 여기서 가장 강력한 고수준 주장을 펼쳤습니다. 동일한 최상위 MacBook Pro 메모리 상한 하에서 "실제로 실행 가능한 가장 스마트한 오픈 웨이트 모델"은 Llama 3 70B 수준에서 **DeepSeek V4 Flash mixed-Q2 GGUF** 수준으로 24개월 만에 약 **4.7배** 향상되었으며, 이는 **10.7개월마다 2배** 향상되는 것을 의미하고, 이는 무어의 법칙보다 빠릅니다. 지지 데이터 포인트는 GGUF 업로드의 급격한 증가에 대한 `@victormustar`의 자료와, **Qwen 3.6**, **Gemma 4**, DeepSeek 변형이 이제 비자명한 에이전트 작업에 로컬에서 사용 가능하다는 반복적인 커뮤니티 관찰에서 나왔습니다.

### 연구 하이라이트: MoE 모듈성, 확산/바이트 모델, 에이전트 역학

**아키텍처와 평가**: AllenAI의 **EMO**는 `@TheTuringPost`에 의해 문서 수준 라우팅이 공유 전문가 풀을 유도하는 더 모듈화된 Mixture-of-Experts 설계로 소개되었습니다. 특히 **전문가의 25%만 유지**하는 것이 유사한 프루닝 하에서 표준 MoE의 **10–15%** 성능 저하에 비해 단 **~1%**의 성능 손실만을 초래한다고 보고합니다(후속 자료). 생성 평가에서는 `@qberthet`이 FID보다 더 빠르고 샘플 효율적인 대체제라고 주장하는 **MIND(Monge Inception Distance)**를 소개했습니다.

**언어 및 바이트 수준 모델링을 위한 확산**: 여러 논문이 비자기회귀(non-AR) 언어 모델링을 발전시켰습니다. `@LucaAmb`는 연속 비트스트림 확산이 자신들의 평가 설정에서 자기회귀 모델에 거의 근접한다고 보고했으며, `@JulieKallini`는 **Fast BLT**를 소개했습니다. 이는 병렬 바이트 디코딩을 위한 확산을 사용하여 바이트 수준 LM의 추론 부담을 줄입니다. `@sriniiyer88`은 이를 블록 바이트 확산과 자기 추측적 디코딩(self-speculative decoding)의 결합으로 프레이밍했습니다. 관련하여 `@LiangZheng_06`은 사후 훈련에서 확산 모델의 유용한 속성을 언급했습니다. 샘플링이 미분 가능하기 때문에 보상 기울기(reward gradient)가 표준 LLM 설정보다 더 직접적으로 파라미터로 흐를 수 있습니다.

**장기 호라이즌에서의 에이전트 행동**: 두 가지 강력한 경험적 흐름이 등장했습니다. 첫째, **"The Memory Curse"**는 모델이 더 **역사를 따르고 위험을 최소화**하게 되어 다중 라운드 사회적 딜레마에서 장기 기억이 협력을 저하시킨다고 주장하며, 명시적인 CoT가 때로는 문제를 증폭시킵니다. 둘째, `@dair_ai`가 요약한 **PwC 연구**는 명확화(clarification)의 가치가 시간에 매우 의존적임을 주장합니다. **목표 명확화는 실행의 ~10% 이후 가치의 대부분을 잃는** 반면, 입력 명확화는 더 오래 유용합니다. 이 두 가지를 종합하면, 장기 호라이즌 에이전트 품질은 원시 모델 IQ만큼이나 메모리/제어 정책에 의해 제한됨을 시사합니다.

**스케일링과 자기 개선**: `@WilliamBarrHeld`가 요약한 Marin의 **Delphi** 스케일링 작업은 소규모 프리트레인에서 **25B / 600B 토큰** 실행으로 외삽할 때 **0.2%**의 예측 오차를 주장합니다. 별도로, `@omarsar0`는 **AutoTTS**를 소개했습니다. 여기서 LLM은 테스트 타임 스케일링 컨트롤러 공간 자체를 탐색하여, 약 **39.9달러**의 발견 비용으로 수작업으로 설계된 전략을 능가한다고 보고합니다.

### /r/LocalLlama + /r/localLLM 요약

#### 1. Qwen 3.6 로컬 추론 발전 — Unsloth의 MTP (활동량: 620)

이미지(링크)는 Unsloth의 Hugging Face 프로필에 새로 게시된 MTP 보존 GGUF 빌드 목록을 보여줍니다: `unsloth/Qwen3.6-27B-GGUF-MTP` 및 `unsloth/Qwen3.6-35B-A3B-GGUF-MTP`. 이 포스트의 기술적 중요성은 이 GGUF들이 MTP / 다음 토큰 예측 레이어를 유지한다는 것이지만, 사용자는 여전히 표준 llama.cpp 지원에 의존하는 대신 특정 llama.cpp MTP PR을 직접 빌드해야 합니다. 한 댓글에서는 27B GGUF에서 런타임/어설션 실패를 보고합니다:

```
GGML_ASSERT(hparams.nextn_predict_layers > 0 && "QWEN35_MTP requires nextn_predict_layers > 0")
```

이는 메타데이터 파싱, 모델 변환, 또는 PR 호환성 문제가 아직 해결되지 않았음을 시사합니다.

댓글들은 업스트림 llama.cpp MTP 지원에 대한 기대를 반영하며, 사용자들은 반복적으로 GitHub 저장소를 확인하고 MTP가 이제 "기본적으로(out of the box)" 지원되는지 묻고 있습니다.

새 **27B** GGUF 모델을 컴파일한 사용자는 `qwen35_mtp.cpp`에서 런타임 어설션 오류가 발생했습니다:

```
GGML_ASSERT(hparams.nextn_predict_layers > 0 && "QWEN35_MTP requires nextn_predict_layers > 0")
```

이는 GGUF/모델 메타데이터 또는 변환 경로에서 Qwen3.5 MTP 추측/다음 토큰 예측 레이어에 필요한 `nextn_predict_layers`가 누락되었을 수 있음을 시사합니다.

한 기술 스레드에서는 **GGUF의 MTP 지원**이 특히 댓글에서 향상된 컨텍스트 길이 처리와 연관 짓는 **35B A3B** 변형에 대한 로컬 추론에 중요하다고 언급합니다. 또 다른 댓글은 이것이 `llama.cpp`가 이제 MTP를 "기본적으로" 지원하는 것을 의미하는지 묻고 있으며, 지원이 병합/안정화되었는지 아니면 PR이나 포크에서만 가능한지에 대한 불확실성을 암시합니다.

한 댓글에서는 현재 **ik_llama** MTP가 **llama.cpp** PR보다 빠르며, 아다마르(Hadamard) 기반 양자화를 지원하는데 이것이 "turboquants"와 유사하다고 주장합니다. 이는 로컬 MTP 추론 백엔드를 비교하는 사용자들에게 잠재적으로 관련된 구현/성능 구분입니다.
