## 📌 학습 정리

### 1. 한 줄로 말하면

이건 코드 전체를 지도로 만들어 두고, AI 코딩 도구가 "지금 고치는 부분과 얽힌 곳만" 골라 읽게 해주는 도구예요. 매번 창고 전체를 뒤지는 대신, 필요한 서랍만 정확히 열어보게 해주는 셈입니다.

### 2. 왜 이게 만들어졌어요?

요즘 AI 코딩 도구에게 "이 코드 좀 리뷰해줘"라고 하면, AI가 관련 있는 곳을 찾겠다고 코드베이스의 상당 부분을 다시 읽어버리는 일이 많아요. 그러면 AI가 한 번에 소화할 수 있는 정보량(토큰, token — AI가 글자를 세는 단위)을 불필요하게 많이 써버리고, 속도도 느려지고 비용도 늘어납니다. 특히 파일이 수천, 수만 개인 큰 저장소일수록 이 낭비가 심해지죠. code-review-graph는 "AI가 매번 전체를 훑지 않아도, 바뀐 곳과 연결된 파일만 콕 집어 읽게 하면 되지 않나?"라는 생각에서 출발했어요. 그래서 코드의 구조를 미리 지도로 그려두고, 리뷰할 때 그 지도를 보고 딱 필요한 파일 목록만 뽑아줍니다.

### 3. 비유로 풀면

이건 마치 큰 도서관에 잘 만들어진 색인 카드와 상호 참조 목록이 있는 것과 같아요. 책 한 권 내용이 바뀌면 "이 책을 인용한 다른 책들이 뭐가 있지?"를 색인만 보고 바로 알 수 있어서, 도서관 전체를 처음부터 다시 읽을 필요가 없죠. 그래서 결국 AI는 "이 파일을 바꿨으니 영향받는 건 이 15개 파일뿐"이라는 답을 지도 조회 한 번으로 얻습니다.

또 하나, 이건 벽돌 하나를 빼면 어디까지 흔들리는지 미리 표시해 둔 건물 도면 같기도 해요. 그래서 결국 코드 한 곳을 고쳤을 때 그 여파(영향 범위)가 어디까지 번지는지를 도면 보듯 추적할 수 있습니다.

### 4. 어떻게 작동하는지 (그림으로)

```mermaid
flowchart TD
    A[내 코드 저장소] --> B[코드 구조를 훑어서<br/>지도로 만들기]
    B --> C[지도 저장<br/>함수·클래스는 점,<br/>호출·상속 관계는 선]
    C --> D{파일을 하나 고침}
    D --> E[지도에서 그 파일과<br/>연결된 곳만 추적]
    E --> F[AI에게 '이 파일들만<br/>읽으면 돼' 하고 전달]
    F --> G[AI가 최소한만 읽고<br/>리뷰/분석]
    D -.바뀐 것만 다시 읽기.-> C
```

먼저 코드 전체를 한 번 훑어서 지도를 만들어 두는데, 이때 함수·클래스 같은 요소는 지도의 '점'이 되고, 서로 부르거나 물려받는 관계는 점을 잇는 '선'이 됩니다. 이후 파일을 고치면 지도를 보고 그 변경과 연결된 곳(부르는 쪽, 의존하는 쪽, 관련 테스트)만 추적해 AI에게 넘겨줘요. 파일을 저장할 때마다 전체를 다시 그리는 게 아니라 바뀐 부분만 갱신하기 때문에, 2,900개 파일짜리 프로젝트도 갱신이 2초 안에 끝난다고 합니다.

### 5. 처음 보는 용어 풀이

- **지식 그래프 / 코드 그래프 (knowledge graph)** — 코드의 구성 요소를 점으로, 그 사이 관계를 선으로 그린 지도예요. "누가 누구를 부르는지"를 한눈에 따라갈 수 있게 정리해 둔 것이라고 보면 됩니다.

- **토큰 (token)** — AI가 글자를 세고 처리하는 최소 단위예요. 토큰을 많이 쓸수록 느리고 비용도 늘어서, 이 도구가 줄이려는 대상이 바로 이겁니다.

- **영향 범위 분석 (blast-radius analysis)** — 한 파일을 바꿨을 때 그 여파가 어디까지 미치는지, 즉 영향받을 수 있는 함수·파일·테스트를 추려주는 기능이에요. "이거 고치면 저기도 깨질 수 있어"를 미리 알려줍니다.

- **추상 구문 트리 (AST, Abstract Syntax Tree)** — 코드를 사람이 읽는 글자가 아니라, 컴퓨터가 이해하기 좋은 구조(나무 모양)로 분해한 표현이에요. 이 도구는 Tree-sitter라는 분석기로 코드를 이 구조로 바꾼 뒤 지도를 만듭니다.

- **점진적 갱신 (incremental updates)** — 코드가 바뀔 때 전체를 다시 분석하지 않고, 바뀐 파일만 골라 다시 읽어 지도를 손보는 방식이에요. 덕분에 매번 처음부터 시작하지 않아 빠릅니다.

- **MCP 서버 (Model Context Protocol)** — AI 코딩 도구가 외부 도구에게 "이 정보 좀 줘"라고 표준 방식으로 요청하게 해주는 연결 규격이에요. code-review-graph는 이 규격의 서버로 동작해서, AI가 알아서 지도를 조회하게 됩니다.

- **의미 기반 검색 (semantic search)** — 단어가 정확히 일치하지 않아도 뜻이 비슷한 코드를 찾아주는 검색이에요. 이 도구에서는 선택 기능이라, 켜지 않아도 기본 지도 기능은 그대로 작동합니다.

- **정밀도와 재현율의 맞바꿈 (precision vs recall trade-off)** — 놓치는 것(재현율)을 줄이려고 일부러 후보를 넉넉히 잡다 보면, 실제로는 상관없는 파일까지 끼는(정밀도 저하) 현상이에요. 이 도구는 "깨질 걸 놓치느니 좀 넉넉하게 표시하자"는 쪽을 택했습니다.

### 6. 한 발 더 들어가고 싶다면

- [code-review-graph GitHub 저장소](https://github.com/tirth8205/code-review-graph) — 설치·명령어·지원 언어 목록 등 도구 전체를 직접 살펴볼 수 있어요.
- [Tree-sitter](https://tree-sitter.github.io/tree-sitter/) — 이 도구가 코드를 구조로 분해할 때 쓰는 분석기가 뭔지 알 수 있어요.
- [MCP (Model Context Protocol)](https://modelcontextprotocol.io) — AI 도구와 외부 도구를 잇는 연결 규격이 어떤 개념인지 알 수 있어요.

AI 코딩 도구는 리뷰 작업에서 코드베이스의 상당 부분을 다시 읽어들이게 되는 경우가 있습니다. `code-review-graph`는 이 문제를 해결합니다. Tree-sitter로 코드의 구조적 지도를 구축하고, 변경 사항을 점진적으로(incrementally) 추적하며, MCP를 통해 AI 어시스턴트에게 정확한 컨텍스트를 제공하여 정말로 필요한 부분만 읽게 합니다.

### Quick Start

```
pip install code-review-graph
# or: pipx install code-review-graph

code-review-graph install   # 지원되는 모든 플랫폼을 자동 감지하고 설정
code-review-graph build     # 코드베이스 파싱
```

한 개의 명령으로 모든 것이 설정됩니다. `install`은 어떤 AI 코딩 도구가 설치되어 있는지 감지하고, 각 도구에 맞는 MCP 설정을 작성하며, 지원되는 곳에는 플랫폼 네이티브 훅/스킬을 설치하고, 플랫폼 규칙(rules)에 그래프 인지(graph-aware) 지침을 주입합니다. `uvx`로 설치했는지 `pip`/`pixx`로 설치했는지 자동 감지하여 올바른 설정을 생성합니다. 설치 후 에디터/도구를 재시작하세요.

특정 플랫폼만 대상으로 하려면:

```
code-review-graph install --platform codex          # Codex만 설정
code-review-graph install --platform cursor         # Cursor만 설정
code-review-graph install --platform claude-code     # Claude Code만 설정
code-review-graph install --platform gemini-cli      # Gemini CLI만 설정
code-review-graph install --platform kiro            # Kiro만 설정
code-review-graph install --platform copilot         # GitHub Copilot(VS Code)만 설정
code-review-graph install --platform copilot-cli      # GitHub Copilot CLI만 설정
code-review-graph install --platform codebuddy        # CodeBuddy Code만 설정
```

Python 3.10 이상이 필요합니다. 최상의 경험을 위해 `uv`를 설치하세요(MCP 설정은 가능하면 `uvx`를 사용하고, 없으면 `code-review-graph` 명령을 직접 사용하도록 폴백합니다).

Git 또는 SVN 프로젝트에서 CRG를 제거하려면, 해당 워킹 트리 내부 어디에서든 대칭적인 uninstall 명령을 사용하세요. 대상은 워킹 트리 루트로 정규화되며, 저장소가 아닌 디렉터리는 거부됩니다. CRG가 소유한 파일과 항목만 제거하며, 관련 없는 MCP 서버·훅·스킬·JSONC 주석은 그대로 남습니다. 공유 설정 변경은 원자적 교체(atomic replacement)를 사용하므로, 쓰기 작업이 실패해도 원본 파일은 손상되지 않습니다.

```
code-review-graph uninstall --dry-run              # 모든 동작을 미리보기; 아무것도 쓰지 않음
code-review-graph uninstall                          # 미리보기 후 확인을 요청하고 적용
code-review-graph uninstall --yes                    # 확인 없이 적용
code-review-graph uninstall --all-repos               # 등록된 모든 저장소도 함께 정리
code-review-graph uninstall --keep-data               # 통합은 제거하되 그래프 데이터베이스는 유지
code-review-graph uninstall --keep-user-configs --repo .   # 이 프로젝트만 정리
```

그런 다음 프로젝트를 열고 AI 어시스턴트에게 다음과 같이 요청하세요:

```
Build the code review graph for this project
```

초기 빌드는 500개 파일 규모의 프로젝트에서 약 10초가 걸립니다. 그 이후에는 watch 모드와 지원되는 훅들이 그래프를 자동으로 계속 최신 상태로 유지할 수 있습니다.

### 동작 방식

여러분의 저장소는 Tree-sitter로 AST로 파싱되고, 노드(함수, 클래스, import)와 엣지(호출, 상속, 테스트 커버리지)로 구성된 그래프로 저장된 다음, 리뷰 시점에 질의(query)되어 AI 어시스턴트가 읽어야 할 최소한의 파일 집합을 계산합니다.

**Blast-radius(폭발 반경) 분석**
파일이 변경되면 그래프는 그 영향을 받을 수 있는 모든 호출자(caller), 의존자(dependent), 테스트를 추적합니다. 이것이 변경의 "blast radius(폭발 반경)"입니다. AI는 전체 프로젝트를 스캔하는 대신 이 파일들만 읽습니다.

**2초 이내 점진적 업데이트**
훅 또는 watch 모드가 활성화되어 있으면, 파일 저장과 지원되는 커밋 훅이 점진적 업데이트를 트리거합니다. 그래프는 변경된 파일을 diff하고, SHA-256 해시 검사를 통해 그 의존자를 찾아, 변경된 부분만 다시 파싱합니다. 2,900개 파일 규모의 프로젝트는 2초 이내에 재인덱싱됩니다.

**모노레포 문제, 해결됨**
대형 모노레포는 토큰 낭비가 가장 심하게 발생하는 지점입니다. 그래프는 이러한 노이즈를 걷어냅니다 — 27,700개 이상의 파일이 리뷰 컨텍스트에서 제외되고, 실제로 읽히는 파일은 약 15개뿐입니다.

**광범위한 언어 지원 + Jupyter 노트북**
파서 지원 범위는 함수, 클래스, import, 호출 지점, 상속, 테스트 탐지를 현재 파서 범위 전역에서 다루며, 가능한 곳에서는 Tree-sitter를 사용하고 필요한 곳에는 표적화된(targeted) 폴백을 사용합니다. 현재 지원 대상은 Python, JavaScript/TypeScript/TSX, Go, Rust, Java, C/C++, C#, VB.NET, Ruby, Kotlin, Swift, PHP, Scala, Solidity, Dart, R, Perl, Lua/Luau, Objective-C, 셸 스크립트, Elixir, Zig, PowerShell, Julia, ReScript, GDScript, Nix, Verilog/SystemVerilog, SQL, Terraform/OpenTofu 구조(`.tf`; 일반 `.hcl` 파일은 파일 노드로만 인식됨), Ansible 플레이북/롤/태스크, Vue/Svelte SFC, TypeScript 파서를 통해 파싱되는 Astro 파일, Jupyter/Databricks 노트북(`.ipynb`), 그리고 Perl XS 파일(`.xs`)입니다. 일반 YAML은 소스 코드로 취급되지 않습니다.

PHP 프로젝트는 추가로 저장소 범위 내(repository-bounded)의 Composer PSR-4 해석(resolution), Blade 템플릿 참조, 그리고 소스에 명시적인 프레임워크 import, 모델 상속, 리시버(receiver) 증거가 포함되어 있을 때 Laravel Route/Eloquent 의미론적 엣지를 지원받습니다.

**자체 언어 추가하기 (포크 불필요)**
여러분의 저장소가 파서가 아직 다루지 않는 언어를 사용한다면, `.code-review-graph/`에 `languages.toml` 파일을 넣어 파일 확장자를 `tree_sitter_language_pack`에 포함된 그래머(grammar)에 매핑하고, 함수·클래스·import·호출에 대한 tree-sitter 노드 타입을 지정하면 됩니다:

```
[languages.erlang]
extensions = [".erl"]
grammar = "erlang"
function_node_types = ["function_clause"]
class_node_types = ["record_decl"]
import_node_types = ["import_attribute"]
call_node_types = ["call"]
```

일반 tree-sitter 워커가 그 지점부터 추출을 처리합니다 — 코드 변경이 필요 없고, 내장 언어는 절대 덮어쓸 수 없습니다. 스키마 참조, 검증 규칙, 그리고 처음부터 끝까지의 실제 예시는 `docs/CUSTOM_LANGUAGES.md`를 참조하세요.

**CI에서의 리스크 점수화(risk-scored) PR 리뷰 (GitHub Action)**
동일한 분석이 컴포지트 GitHub Action으로도 실행되며 — 그리고 이 역시 로컬 우선(local-first)을 유지합니다: 지식 그래프는 전적으로 여러분의 CI 러너 위에서 구축되고 질의되며, 어떤 외부 서비스로도 소스 코드가 전송되지 않습니다. 각 풀 리퀘스트마다 이 액션은 리스크 점수가 부여된 함수, 영향을 받는 실행 흐름(execution flow), 테스트 공백을 담은 단일 스티키 코멘트(sticky comment)를 게시하며, 매 푸시마다 그 자리에서 갱신됩니다. 선택적인 `fail-on-risk` 입력을 사용하면 리뷰를 머지 게이트(merge gate)로 만들 수 있습니다.

```
# .github/workflows/code-review-graph.yml
on:
  pull_request:

permissions:
  contents: read
  pull-requests: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: tirth8205/code-review-graph@v2.3.6
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
```

입력값, 리스크 레벨, 캐싱 세부사항에 대해서는 `docs/GITHUB_ACTION.md`를, 혹은 이 저장소가 스스로에게 사용하는 dogfood 워크플로우인 `.github/workflows/pr-review.yml`을 참조하세요.

### Benchmarks

**헤드라인 수치**: 6개 저장소에 걸친 질문당 토큰 절감의 중앙값은 약 82배(전체 코퍼스 기준선 대비 그래프 질의)입니다. 흔히 인용되는 528배는 최댓값 — 단일 최상 사례(fastapi) — 이며 일반적인 결과가 아닙니다.

모든 수치는 6개의 실제 오픈소스 저장소(총 13개 커밋)에 대한 자동화된 평가 러너에서 나온 것입니다. 모든 설정은 업스트림 SHA를 고정하고, Leiden 커뮤니티 탐지기는 고정된 시드로 실행되며, 임베딩은 CPU에서 결정적(deterministic)입니다 — 따라서 서로 다른 머신에서 두 번 실행해도 동일한 수치가 나옵니다. 예상 출력을 포함한 전체 재현 레시피는 `docs/REPRODUCING.md`에 있습니다. 가장 작은 두 구성에 대한 주간 report-only 실행은 `.github/workflows/eval.yml`에 있습니다.

**토큰 효율성**: 질문당 평균 약 82배 절감(범위 38배 – 528배; 전체 코퍼스 대비 그래프 질의)

일반적인 에이전트 질문(예: "인증은 어떻게 동작하는가", "메인 진입점은 무엇인가" 등)에 대해, 그래프는 에이전트가 모든 소스 파일을 읽도록 강제하는 대신 약 2,000~3,500 토큰 규모의 표적 검색 결과 + 인접 엣지(neighbor edge)를 반환합니다. 아래 표는 `code_review_graph/token_benchmark.py`에 정의된 5개 샘플 질문에 대한 평균입니다.

| 저장소 | 스냅샷 SHA | naive_corpus_tokens | avg graph_tokens | 절감률 |
|---|---|---|---|---|
| fastapi | 0227991a | 951,071 | 2,169 | 528.4x |
| code-review-graph | 84bde354 | 208,821 | 2,495 | 93.0x |
| gin | 5c00df8a | 166,868 | 1,990 | 91.8x |
| flask | a29f88ce | 125,022 | 1,986 | 71.4x |
| express | b4ab7d65 | 135,955 | 3,465 | 40.6x |
| httpx | b55d4635 | 89,492 | 2,438 | 38.0x |

6개 저장소에 걸친 질문당 절감률의 중앙값: 약 82배. 범위는 38배 – 528배이며, 528배는 최상의 사례(fastapi, 가장 큰 코퍼스)이지 헤드라인 수치가 아닙니다.

위의 전체 코퍼스 기준선은 실제 에이전트라면 지불하지 않을 상한선입니다: 능숙한 에이전트는 식별자를 grep하고 가장 잘 일치하는 파일만 읽습니다. `agent_baseline` 평가 벤치마크는 그 현실적인 기준선을 측정합니다 — 코퍼스에 대한 순수 파이썬 grep으로, 일치 횟수 기준 상위 3개 파일을 선정하고, 토큰을 계산하여 그래프 질의 비용과 비교합니다(`evaluate/results/<repo>_agent_baseline_*.csv`).

정식 `eval/benchmarks/token_efficiency.py` 벤치마크는 다른 시나리오를 측정합니다 — 전체 `get_review_context()` JSON 대비 커밋의 변경된 파일 콘텐츠만을 비교하는 것으로, 작은 커밋에서는 1 미만의 비율을 보이는데, 이는 리뷰 컨텍스트 응답이 임팩트 반경(impact-radius) 엣지와 소스 스니펫을 함께 포함하여 아주 작은 단일 파일 diff보다 커지기 때문입니다. 이는 버그가 아니라, 두 벤치마크가 서로 다른 질문에 답하고 있는 것입니다. 전체 방법론은 `docs/REPRODUCING.md`를 참조하세요.

v2.3.4부터, 리뷰 및 임팩트 도구는 간결한 `context_savings` 추정치를 첨부하여 MCP 클라이언트가 호출당 절감된 대략적인 컨텍스트 양을 볼 수 있게 합니다. v2.3.5에서는 CLI가 이를 위 "Usage" 섹션의 "Token Savings panel"에서 보여준 박스형 Token Savings 패널로 표면화하며, OpenAI의 `cl100k_base` 토크나이저와 교차 검증하는 `--verify`를 추가합니다. `docs/REPRODUCING.md`의 캘리브레이션 데이터에 따르면 이 추정치는 222개 샘플 파일 전체에서 실제 GPT-4 토큰과 약 1% 이내의 오차를 보입니다.

**임팩트 정확도**: 그래프 유래(graph-derived) 정답 대비 평균 F1 0.71 (재현율 1.0은 순환적인 상한선이며 "100% 재현율"이 아님)

Blast-radius 분석은 13개의 평가 커밋 전체에서 정답(ground truth)에 있는 모든 파일을 복원합니다 — 하지만 이를 상한선으로 읽어야 하며 "100% 재현율"로 읽어서는 안 됩니다: 이 모드에서 정답(변경된 파일 + 그 파일로 들어오는 호출/import 엣지를 가진 파일)은 예측기가 순회하는 것과 동일한 그래프에서 도출되므로, 구조상 순환적입니다. 정밀도(precision) 열에서 보이는 과잉 예측은 의도적인 트레이드오프입니다: 의존성 누락을 놓치는 것보다는 너무 많은 파일을 표시하는 쪽이 낫다는 판단입니다.

| 저장소 | 커밋 수 | 평균 F1 | 평균 정밀도 | 재현율(그래프 유래 상한선) |
|---|---|---|---|---|
| httpx | 2 | 0.864 | 0.786 | 1.0 |
| fastapi | 2 | 0.834 | 0.750 | 1.0 |
| code-review-graph | 2 | 0.734 | 0.584 | 1.0 |
| express | 2 | 0.667 | 0.500 | 1.0 |
| flask | 2 | 0.628 | 0.481 | 1.0 |
| gin | 3 | 0.609 | 0.439 | 1.0 |
| 평균 | 13 | 0.714 | 0.578 | 1.000 |

이 벤치마크는 또한 정직한 co-change 모드도 실행합니다: 예측기는 단일 변경 파일로 시드(seed)되고, 저자가 같은 커밋에서 실제로 수정한 다른 파일들 — 그래프가 아니라 git 히스토리에서 나온 독립적인(-ish) 증거 — 을 기준으로 채점됩니다. 두 모드 모두 결과 CSV에 나란히 나타납니다(`ground_truth_mode` 열). Co-change 수치는 평가 러너로 측정되는 대로 정본 통계에 추가될 것입니다; 측정 전에는 인용하지 않습니다.

**한계와 알려진 약점**

- **임팩트 "재현율 1.0"은 그래프 유래이며 순환적입니다**: 과거 정답 데이터는 예측기가 순회하는 것과 동일한 그래프 엣지에서 나오므로, 구조상 상한선입니다. 정직한 co-change 모드(동일 커밋에서 실제로 함께 변경된 파일 대비 채점)가 함께 측정되고 있으며, 그 수치는 상당히 낮을 것으로 예상됩니다.
- **작은 단일 파일 변경**: 그래프 컨텍스트가 사소한 편집에 대해서는 naive 파일 읽기보다 클 수 있습니다(위 express 결과 참조). 그 오버헤드는 다중 파일 분석을 가능하게 하는 구조적 메타데이터입니다.
- **검색 품질(MRR 0.35)**: 키워드 검색은 대부분의 질의에서 상위 4개 안에 정답을 찾아내지만, 랭킹은 개선이 필요합니다. Express 질의는 모듈 패턴 네이밍 때문에 0건의 히트를 반환합니다.
- **흐름 탐지(재현율 33%)**: 프레임워크 및 관례적 진입점 패턴은 Python과 PHP/Laravel에서 가장 강력합니다. JavaScript와 Go의 흐름 탐지는 개선이 필요합니다.
- **정밀도 대 재현율 트레이드오프**: 임팩트 분석은 의도적으로 보수적입니다. 영향을 받을 수 있는 파일을 표시하므로, 대형 의존성 그래프에서는 일부 거짓 양성(false positive)이 발생합니다.

```
code-review-graph detect-changes --brief --verify       # tiktoken과 교차 검증
code-review-graph register <path>                       # 멀티 저장소 레지스트리에 저장소 등록
code-review-graph unregister <id>                        # 레지스트리에서 저장소 제거
code-review-graph repos                                  # 등록된 저장소 목록
code-review-graph daemon start                            # 멀티 저장소 watch 데몬 시작
code-review-graph daemon stop                             # 데몬 정지
code-review-graph daemon status                           # 데몬 상태와 저장소 표시
code-review-graph eval                                   # 평가 벤치마크 실행
code-review-graph serve                                  # MCP 서버 시작
```

JSON 내보내기는 기본적으로 Git이 무시하는 로컬 그래프 데이터 디렉터리 안에만 남습니다. 절대경로와 코드 구조 메타데이터를 포함할 수 있으므로, 자신의 머신 밖으로 게시하기 전에 내보내기 결과를 점검하고 정제(sanitize)하세요.

**Token Savings 패널: `detect-changes --brief` 대 `update --brief`**

두 명령 모두 동일한 간결한 패널을 출력하여, 변경된 파일을 그대로 에이전트에 넘기는 것과 비교해 그래프가 얼마나 많은 토큰을 절감했는지를 보여줍니다. 둘의 차이는 오직 한 가지입니다: 그래프를 먼저 갱신할지 여부.

```
┌─────────────────────── Token Savings ────────────────────────┐
│ Full context would be:     12,921 tokens                     │
│ Graph context used:           762 tokens                     │
│ Saved:                     12,159 tokens (~94%)              │
│ Breakdown: Functions 244 · Tests 191 · Risk 244 · Other 83   │
└──────────────────────────────────────────────────────────────┘
```

| 명령 | 동작 | 사용 시점 |
|---|---|---|
| `detect-changes --brief` | 읽기 전용. 현재 변경 사항을 보고, 기존 그래프를 질의하여, 패널을 출력. 약 1초. | 대부분의 경우 — 훅(또는 `crg-daemon`)이 백그라운드에서 그래프를 최신 상태로 유지하므로 이것으로 충분함. |
| `update --brief` | 변경된 파일을 그래프에 먼저 다시 파싱한 뒤, 동일한 패널을 출력. 약 5초. | 리베이스 이후, 대량 변경 세트 이후, 또는 그래프가 오래됐다고 의심될 때 언제든. |

두 명령 모두 마지막에 동일한 `analyze_changes()` 단계를 호출하기 때문에 동일한 패널로 끝납니다. 차이는 그 분석이 실행되기 전에 그래프 자체가 갱신됐는지 여부입니다.

두 명령 중 어느 쪽에든 `--verify`를 추가하면 표시된 수치를 OpenAI의 `cl100k_base` 토크나이저(GPT-4 계열)와 교차 검증합니다. `pip install tiktoken`이 필요합니다. 이 추정치는 일반적인 변경 세트에서 실제 토큰과 약 1% 이내로 유지됩니다 — 캘리브레이션 데이터는 `docs/REPRODUCING.md`를 참조하세요.

동일한 `context_savings` 메타데이터는 `get_impact_radius`, `get_review_context`, `detect_changes`, `get_architecture_overview` MCP 도구의 JSON 응답에도 자동으로 첨부되므로, AI 에이전트는 별도의 프롬프팅 없이 채팅에서 절감량을 사람에게 표면화할 수 있습니다.

**멀티 저장소 데몬**

여러분의 에디터가 훅을 지원하지 않는다면(예: Cursor, OpenCode), 또는 그냥 에디터 통합 없이도 그래프가 백그라운드에서 항상 최신 상태를 유지하기를 원한다면, 데몬이 그 용도에 맞습니다. 저장소들의 파일 변경을 watch하며 그래프를 자동으로 재구축합니다 — 수동으로 `build`나 `update` 명령을 실행할 필요가 없습니다.

데몬은 `code-review-graph`에 포함되어 있습니다 — 별도 설치가 필요 없습니다.

**빠른 설정:**

```
# 1. watch할 저장소를 등록
crg-daemon add ~/project-a --alias proj-a
crg-daemon add ~/project-b

# 2. 데몬 시작(백그라운드에서 실행)
crg-daemon start

# 3. 그게 끝 — 그래프는 자동으로 최신 상태로 유지됨
crg-daemon status                # 데몬과 저장소별 watcher 상태 확인
crg-daemon logs --repo proj-a -f  # 특정 저장소의 로그 tail
crg-daemon stop                   # 데몬과 모든 watcher 프로세스 정지
```

`code-review-graph daemon start|stop|status|...`로도 사용할 수 있습니다.

내부적으로 `crg-daemon add`는 `~/.code-review-graph/watch.toml`의 TOML 설정 파일에 기록합니다. 이 파일을 직접 편집할 수도 있습니다:

```
[[repos]]
path = "/home/user/project-a"
alias = "proj-a"

[[repos]]
path = "/home/user/project-b"
alias = "project-b"
```

데몬은 이 설정 파일의 변경을 감시하여 저장소가 추가/제거될 때 watcher 프로세스를 자동으로 시작/정지합니다. 30초마다 헬스체크가 죽은 watcher를 재시작합니다. 외부 의존성은 필요 없습니다.

전체 설정 참조와 사용 가능한 모든 옵션은 `docs/COMMANDS.md`를 참조하세요.

### Configuration

인덱싱에서 경로를 제외하려면, 저장소 루트에 `.code-review-graphignore` 파일을 생성하세요:

```
generated/**
*.generated.ts
vendor/**
node_modules/**
```

참고: git 저장소에서는 추적되는 파일만 인덱싱되므로(`git ls-files`), gitignore된 파일은 자동으로 건너뜁니다. `.code-review-graphignore`는 추적되는 파일을 제외하거나 git을 사용할 수 없을 때 사용하세요.

**선택적 의존성 그룹:**

```
pip install "code-review-graph[embeddings]"          # 로컬 벡터 임베딩(sentence-transformers)
pip install "code-review-graph[google-embeddings]"     # Google Gemini 임베딩
pip install "code-review-graph[communities]"           # 커뮤니티 탐지(igraph)
pip install "code-review-graph[enrichment]"            # Python 호출 해석 강화(Jedi)
pip install "code-review-graph[eval]"                  # 평가 벤치마크(matplotlib)
pip install "code-review-graph[wiki]"                  # LLM 요약을 이용한 위키 생성(ollama)
pip install "code-review-graph[all]"                   # 모든 선택적 의존성
```

OpenAI 호환 임베딩(실제 OpenAI, Azure, 또는 new-api/LiteLLM/vLLM/LocalAI/openai 모드의 Ollama와 같은 자체 호스팅 게이트웨이 어떤 것이든)은 추가 설치가 필요 없습니다 — 환경 변수를 설정하고 `embed_graph`에 `provider="openai"`를 전달하기만 하면 됩니다:

```
export CRG_OPENAI_BASE_URL=http://127.0.0.1:3000/v1   # 또는 https://api.openai.com/v1
export CRG_OPENAI_API_KEY=sk-...
export CRG_OPENAI_MODEL=text-embedding-3-small          # 여러분의 게이트웨이가 제공하는 것

# 선택 사항:
export CRG_OPENAI_DIMENSION=1536       # 차원 고정(v3 모델은 축소를 지원)
export CRG_OPENAI_BATCH_SIZE=100       # 제한이 엄격한 게이트웨이용으로 낮추기
                                        # (예: Qwen text-embedding-v4는 10으로 상한)
```

클라우드 egress 경고는 base URL이 localhost(`127.0.0.1`, `localhost`, `0.0.0.0`, `::1`)를 가리킬 때 자동으로 건너뜁니다.

**모델 선택 팁.** 장기간 유지할 계획이 있는 용도로는 `-preview`/`-beta`/`-exp` 모델 ID(예: `google/gemini-embedding-2-preview`)를 피하세요 — 프리뷰 모델은 가중치가 바뀔 수 있고(차원이 달라지면 전체 재임베딩이 필요함), 사전 공지 없이 폐기(deprecate)될 수 있습니다. `text-embedding-3-small`/`text-embedding-3-large`(OpenAI), `Qwen/Qwen3-Embedding-8B`(자체 호스팅 vLLM/LocalAI를 통해), 또는 `gemini-embedding-001`(네이티브 Gemini 프로바이더를 통해 — 이는 OpenAI 호환 경로가 아니라 `GOOGLE_API_KEY`가 필요함)과 같은 안정적인 GA 릴리스를 선호하세요.

`code-review-graph`는 식별자, 시그니처, 구조적 컨텍스트, 그리고 범위가 제한된 첫 문단의 docstring/doc-comment 요약을 임베딩합니다. 함수 본문은 전송하지 않습니다. 문서 추출이 추가되기 전에 생성된 그래프는 모든 파일이 다시 파싱되도록 재임베딩 전에 한 번의 전체 `code-review-graph build`가 필요합니다. 정기적인 빌드는 기본적으로 임베딩을 갱신하지 않습니다. 빌드 이후 기존 인덱스를 갱신하려면 `--embedding-provider`와 `--embedding-model`을 명시적으로 둘 다 전달하세요; 클라우드 선택은 이 소스 유래 텍스트를 전송하고 API 비용이 발생할 수 있습니다.

**Tool Filtering**

CRG는 기본적으로 30개의 MCP 도구를 노출합니다. 토큰이 제한된 환경에서는, `--tools` 또는 `CRG_TOOLS` 환경 변수를 사용하여 서버를 도구의 부분집합으로 제한할 수 있습니다:

```
# CLI 플래그를 통해
code-review-graph serve --tools query_graph_tool,semantic_search_nodes_tool,detect_changes_tool

# 환경 변수를 통해
CRG_TOOLS=query_graph_tool,semantic_search_nodes_tool code-review-graph serve
```

CLI 플래그가 환경 변수보다 우선합니다. 둘 다 설정되지 않으면 모든 도구를 사용할 수 있습니다. 이는 특히 MCP 클라이언트 설정에서 유용합니다:

```
{
  "mcpServers": {
    "code-review-graph": {
      "command": "code-review-graph",
      "args": [
        "serve",
        "--tools",
        "query_graph_tool,semantic_search_nodes_tool,detect_changes_tool,get_review_context_tool"
      ]
    }
  }
}
```

### FAQ & how it compares

`docs/FAQ.md`에 있는 짧고 정직한 답변들:

- **vs LSP / language server** — 언어별 데몬 여러 개 대신 언어 전역에 걸친 하나의 지속적인 그래프; LSP는 심볼 단위로는 여전히 더 정밀함.
- **vs RAG / embeddings** — 유사도 청크가 아니라 AST에서 파싱된 구조적 엣지; 임베딩은 선택적이며 검색을 보조할 뿐임.
- **vs grep / agentic search** — 단일 홉(one-hop) 조회는 grep이 이기고, 다중 홉 질문(임팩트 반경, 호출자의 호출자, ~에 대한 테스트, 영향받는 흐름)은 그래프가 이김.
- **vs Serena, codegraph, claude-context, repomix** — 사실 기반 비교표.
- **언제 사용하지 말아야 하는가** — 소형 저장소, 사소한 단일 파일 diff, 일회성 질문.
- **홈으로 전화(phone home)를 하는가?** — 아니요; 텔레메트리 없음, 클라우드 임베딩은 opt-in.
- **동작 여부는 어떻게 확인하는가?** — `status`, `detect-changes --brief`, `/mcp`.
