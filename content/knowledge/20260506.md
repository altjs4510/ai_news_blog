## 📌 학습 정리

### 1. 한 줄 정의
**Matt Pocock**이 매일 실전 엔지니어링에 쓰는 **Claude Code/Codex 호환 스킬 모음**으로, **GSD/BMAD/Spec-Kit**처럼 프로세스를 통째로 가져가지 않고 **작고 조합 가능한(skills)** 단위로 에이전트 실패 모드를 교정한다.

### 2. 왜 지금 중요한가
- **에이전트 스킬 표준화 흐름**: `commands/agents/skills/hooks` 4종 구조를 한 저장소에서 일관되게 보여주는 사실상 첫 대규모 레퍼런스(공개 1주일 만에 3.1만 스타).
- **"에이전트 자율"에서 "엔지니어 통제"로 회귀**: GSD/BMAD/Spec-Kit이 프로세스를 빼앗는 문제를 지적하며, 작고 해킹 가능한 스킬을 강조 — 사내 표준화에 그대로 적용 가능한 철학.
- **공유 언어(Ubiquitous Language)의 에이전트화**: `CONTEXT.md` + `docs/adr/`로 도메인 용어집을 코드화해 토큰·verbosity·일관성을 동시 해결.
- **피드백 루프 결핍이 LLM 코드 품질의 본질 문제**라는 진단을 `tdd`(red-green-refactor) · `diagnose`로 명시화.
- **AI가 가속하는 소프트웨어 엔트로피** 문제에 `improve-codebase-architecture`로 주기적 정비 루틴을 제시 — "ball of mud" 방지가 곧 운영 비용.

### 3. 핵심 개념

| 용어 | 정의 | 비고/관련 키워드 |
|---|---|---|
| **Skill** | 모델 무관(any model)·작고 조합 가능한 에이전트 작업 단위 | GSD/BMAD/Spec-Kit 대비 control 보존 |
| **Grilling Session** | 에이전트가 사용자에게 상세 질문을 던져 정렬을 강제하는 단계 | `/grill-me`, `/grill-with-docs` |
| **Shared Language / CONTEXT.md** | 프로젝트 도메인 용어를 에이전트와 공유하는 문서 | DDD Ubiquitous Language, "materialization cascade" 예시 |
| **ADR (`docs/adr/`)** | 설명 어려운 결정을 기록하는 아키텍처 결정 문서 | `/grill-with-docs`가 inline 갱신 |
| **Red-Green-Refactor** | 실패 테스트 → 통과 → 리팩터의 TDD 루프 | `/tdd` 스킬 |
| **Diagnosis Loop** | reproduce → minimise → hypothesise → instrument → fix → regression-test | `/diagnose` |
| **Vertical Slice** | 독립적으로 집을 수 있는 작업 단위로 분해 | `/to-issues`, `/tdd` |
| **Deepening (Ousterhout)** | 단순 인터페이스 뒤에 깊은 모듈을 두는 설계 전략 | `/improve-codebase-architecture` |
| **Triage State Machine** | 라벨 기반 역할 전이로 이슈 분류 | `/triage`, `/setup-matt-pocock-skills` |
| **Caveman Mode** | filler 제거로 토큰 ~75% 절감하는 압축 통신 모드 | productivity skill |
| **Git Guardrails Hooks** | `push`/`reset --hard`/`clean` 등 위험 명령 차단 | Claude Code hooks 사용 사례 |

    G1[/grill-me/]

  subgraph Build[실행 레이어]
    TDD[/tdd<br/>red-green-refactor/]
    DIAG[/diagnose/]

  end

  subgraph Maint[정비 레이어]

핵심은 **3계층 루프**: (1) 정렬(grill → CONTEXT.md/ADR → PRD → issues) → (2) 실행(tdd/diagnose/zoom-out) → (3) 정비(improve-architecture/triage). `setup-matt-pocock-skills`가 issue tracker(GitHub/Linear/local), triage 라벨 어휘, 도메인 문서 위치를 1회 부트스트랩하고 나머지 스킬이 이 설정을 소비한다.

### 6. 사용자 프로젝트 접목

- **DCSAI `dcs-ai-plugin`(Claude Code plugin) 재정비**: 현재 plugin의 skills/agents/hooks를 Matt 저장소의 3계층(정렬·실행·정비)으로 재배열. 사내 버전으로 `/grill-with-docs`를 포크해 **Anthropic SDK 직통합 agent loop**의 시스템 프롬프트에 사내 도메인 용어집(`CONTEXT.md`)을 주입하고, **HITL 분기 지점**에서 `/grill-me`를 자동 호출해 misalignment 단계를 의무화.
- **DCSAI `ff-claude-manager`(Tauri 2) 배포 채널**: Matt가 제시한 `setup-matt-pocock-skills` 부트스트랩 패턴을 차용해, 사내 표준 스킬셋(코드리뷰·**KG 질의**·**Snowflake 분석**·MCP host 호출) 설치/업데이트를 매니저 자동 채널로 푸시. `git-guardrails-claude-code` 훅은 사내 모노레포에 즉시 이식 가능한 PoC.
- **DCSAI MCP host 측**: `/improve-codebase-architecture`의 "deepening" 관점으로 자체 구현한 MCP host server의 모듈 인터페이스를 점검, FSD 프런트엔드와의 경계 재설계. `/diagnose` 루프를 **HTTP chunked streaming** 회귀 버그 추적 SOP로 표준화.
- **Team Agent — `brand.yaml` × CONTEXT.md 결합**: 브랜드별 `brand.yaml`을 Matt식 **공유 언어** 문서로 확장해 `discovery-core-agent`(브랜드)에 주입, `platform-core-agent`(크로스 브랜드)는 ADR 레이어를 소유. `/grill-with-docs` 패턴으로 브랜드 도메인 전문가와의 정렬 세션을 **Activity Log/Observer L1~L4**에 기록 자산으로 축적.
- **Team Agent — Quest 3계층 ↔ to-prd/to-issues**: `/to-prd` → `/to-issues`(vertical slice)를 **Quest 전체·파티·플레이어 3계층** 분해기로 매핑. Goal 2축(Build/Operate)에서 Build 측 하네스의 PRD→Issue 파이프라인으로 채택하고, **server-only 경계**의 변경은 `/zoom-out`으로 컨텍스트를 강제 확장한 뒤 진행.

# 실제 엔지니어를 위한 Skills

매일 실제 엔지니어링에 사용하는 나의 에이전트 스킬 모음 — 분위기에 휩쓸리는 코딩(vibe coding)이 아닌.

실제 애플리케이션을 개발하는 것은 어렵다. GSD, BMAD, Spec-Kit 같은 접근 방식은 프로세스를 전담 관리함으로써 도움을 주려 한다. 그러나 그 과정에서 당신의 통제권을 빼앗고, 프로세스 내 버그를 해결하기 어렵게 만든다.

이 스킬들은 작고, 적용하기 쉬우며, 조합 가능하도록 설계되었다. 어떤 모델에서도 동작한다. 수십 년의 엔지니어링 경험을 기반으로 한다. 마음껏 손봐라. 자신만의 것으로 만들어라. 즐겨라.

이 스킬들의 변경 사항과 새로 만드는 스킬들을 계속 받아보고 싶다면, 내 뉴스레터에서 다른 ~60,000명의 개발자들과 함께할 수 있다:

## 이 스킬들이 존재하는 이유

나는 Claude Code, Codex, 그리고 다른 코딩 에이전트에서 자주 발생하는 실패 패턴을 고치기 위해 이 스킬들을 만들었다.

---

### #1: 에이전트가 내가 원하는 것을 하지 않는다

> "아무도 자신이 정확히 무엇을 원하는지 모른다"
>
> — David Thomas & Andrew Hunt, *The Pragmatic Programmer*

**문제.** 소프트웨어 개발에서 가장 흔한 실패 패턴은 불일치(misalignment)다. 당신은 개발자가 당신이 원하는 것을 안다고 생각한다. 그런 다음 그들이 만든 것을 보면 — 전혀 이해하지 못했다는 것을 깨닫는다.

AI 시대에도 마찬가지다. 당신과 에이전트 사이에는 커뮤니케이션 갭이 있다. 이를 해결하는 방법은 **그릴링 세션(grilling session)** 이다 — 에이전트가 당신이 만들고 있는 것에 대해 상세한 질문을 하도록 만드는 것.

**해결책**은 다음을 사용하는 것이다:

- `/grill-me` — 코드가 아닌 용도에 사용
- `/grill-with-docs` — `/grill-me`와 동일하지만 더 많은 기능 추가 (아래 참조)

이것들은 내 가장 인기 있는 스킬이다. 시작하기 전에 에이전트와 정렬(align)하고, 당신이 만들고 있는 변경에 대해 깊이 생각하도록 도와준다. 변경을 원할 때마다 **매번** 사용하라.

---

### #2: 에이전트가 너무 장황하다

> "유비쿼터스 언어(ubiquitous language)를 사용하면, 개발자들 간의 대화와 코드 표현이 모두 동일한 도메인 모델에서 파생된다."
>
> — Eric Evans, *Domain-Driven-Design*

**문제**: 프로젝트 초반에, 개발자와 소프트웨어를 만들어달라고 요청하는 사람들(도메인 전문가)은 대개 서로 다른 언어를 사용한다.

나도 에이전트와 같은 긴장감을 느꼈다. 에이전트는 보통 프로젝트에 투입되어 전문 용어를 즉석에서 파악하도록 요청받는다. 그래서 1개의 단어로 충분한 곳에 20개의 단어를 사용한다.

**해결책**은 공유 언어(shared language)다. 이것은 에이전트가 프로젝트에서 사용되는 전문 용어를 해독하도록 도와주는 문서다.

**예시**

내 `course-video-manager` 저장소의 `CONTEXT.md` 예시가 있다. 어느 것이 읽기 더 쉬운가?

**이전**: "커스(course)의 섹션(section) 안에 있는 레슨(lesson)이 '실재화(real)'될 때 (즉, 파일 시스템에서 자리를 부여받을 때) 문제가 발생한다"

**이후**: "materialization cascade에 문제가 있다"

이 간결함은 세션마다 계속해서 효과를 발휘한다.

이것은 `/grill-with-docs`에 내장되어 있다. 이것은 그릴링 세션이지만, AI와 공유 언어를 구축하고, 설명하기 어려운 결정들을 ADR(Architecture Decision Record)로 문서화하는 데 도움을 준다.

이것이 얼마나 강력한지 설명하기 어렵다. 이 저장소에서 단 하나의 가장 멋진 기법일 수도 있다. 직접 써보라.

> **팁**
>
> 공유 언어는 장황함을 줄이는 것 외에도 많은 이점이 있다:
> - **변수, 함수, 파일이 일관되게 명명된다**, 공유 언어를 사용하여
> - 그 결과, **코드베이스를 에이전트가 탐색하기 더 쉬워진다**
> - 에이전트가 더 간결한 언어를 사용할 수 있기 때문에 **생각하는 데 소비하는 토큰도 줄어든다**

---

### #3: 코드가 동작하지 않는다

> "항상 작고 신중한 단계를 밟아라. 피드백 속도가 당신의 속도 제한이다. 너무 큰 작업은 절대 맡지 마라."
>
> — David Thomas & Andrew Hunt, *The Pragmatic Programmer*

**문제**: 당신과 에이전트가 무엇을 만들지 정렬되었다고 가정하자. 에이전트가 **그래도** 형편없는 결과물을 낸다면 어떻게 할 것인가?

피드백 루프를 살펴볼 시간이다. 에이전트가 생성한 코드가 실제로 어떻게 실행되는지에 대한 피드백 없이는, 에이전트는 눈을 감고 날아가는 것과 같다.

**해결책**: 일반적인 피드백 루프 일체가 필요하다: 정적 타입, 브라우저 접근, 그리고 자동화된 테스트.

자동화된 테스트에 있어서, 레드-그린-리팩터(red-green-refactor) 루프가 매우 중요하다. 이것은 에이전트가 먼저 실패하는 테스트를 작성한 다음, 테스트를 통과시키는 방식이다. 이는 에이전트에게 일관된 수준의 피드백을 제공하여 훨씬 나은 코드를 만들어낸다.

어떤 프로젝트에도 슬롯처럼 끼워 넣을 수 있는 `/tdd` 스킬을 만들었다. 레드-그린-리팩터를 권장하고, 좋은 테스트와 나쁜 테스트가 무엇인지에 대한 충분한 지침을 에이전트에게 제공한다.

디버깅을 위해서는, 최선의 디버깅 관행을 간단한 루프로 감싼 `/diagnose` 스킬도 만들었다.

---

### #4: 진흙 덩어리(Ball of Mud)를 만들어버렸다

> "시스템 설계에 **매일** 투자하라."
>
> — Kent Beck, *Extreme Programming Explained*

> "최선의 모듈은 깊다. 단순한 인터페이스를 통해 많은 기능에 접근할 수 있게 한다."
>
> — John Ousterhout, *A Philosophy Of Software Design*

**문제**: 에이전트로 만든 대부분의 앱은 복잡하고 변경하기 어렵다. 에이전트가 코딩 속도를 급격히 높일 수 있기 때문에, 소프트웨어 엔트로피도 가속화된다. 코드베이스는 전례 없는 속도로 복잡해진다.

**해결책**은 AI 기반 개발에 대한 근본적으로 새로운 접근 방식이다: 코드 설계에 신경 쓰는 것.

이것은 이 스킬들의 모든 레이어에 내장되어 있다:

- `/to-prd`는 PRD를 생성하기 전에 어떤 모듈을 건드리는지 질문한다
- `/zoom-out`은 에이전트에게 전체 시스템의 맥락에서 코드를 설명하도록 지시한다
- 그리고 결정적으로, `/improve-codebase-architecture`는 진흙 덩어리가 되어버린 코드베이스를 구출하는 데 도움을 준다. 며칠에 한 번씩 코드베이스에서 실행하는 것을 권장한다.

---

## 요약

소프트웨어 엔지니어링의 기본은 그 어느 때보다 중요하다. 이 스킬들은 이러한 기본을 반복 가능한 실천으로 압축하여, 당신의 커리어 최고의 앱을 출시하는 데 도움을 주기 위한 나의 최선의 노력이다. 즐겨라.

## 레퍼런스

### 엔지니어링

코드 작업을 위해 매일 사용하는 스킬.

- **diagnose** — 어려운 버그와 성능 회귀를 위한 체계적인 진단 루프: 재현 → 최소화 → 가설 설정 → 계측 → 수정 → 회귀 테스트.
- **grill-with-docs** — 기존 도메인 모델에 대해 당신의 계획에 도전하고, 용어를 정제하며, `CONTEXT.md`와 ADR을 인라인으로 업데이트하는 그릴링 세션.
- **triage** — 트리아지 역할의 상태 머신을 통해 이슈를 트리아지한다.
- **improve-codebase-architecture** — `CONTEXT.md`의 도메인 언어와 `docs/adr/`의 결정들을 참고하여, 코드베이스에서 심화(deepening) 기회를 찾아낸다.
- **setup-matt-pocock-skills** — 다른 엔지니어링 스킬들이 사용하는 저장소별 설정(이슈 트래커, 트리아지 레이블 어휘, 도메인 문서 레이아웃)을 스캐폴딩한다. `to-issues`, `to-prd`, `triage`, `diagnose`, `tdd`, `improve-codebase-architecture`, 또는 `zoom-out`을 사용하기 전에 저장소당 한 번 실행한다.
- **tdd** — 레드-그린-리팩터 루프를 사용한 테스트 주도 개발(Test-Driven Development). 한 번에 하나의 수직 슬라이스(vertical slice)씩 기능을 만들거나 버그를 수정한다.
- **to-issues** — 어떤 계획, 명세, 또는 PRD도 수직 슬라이스를 사용하여 독립적으로 처리 가능한 GitHub 이슈로 분해한다.
- **to-prd** — 현재 대화 컨텍스트를 PRD로 변환하고 GitHub 이슈로 제출한다. 인터뷰 없이 — 이미 논의한 내용을 종합할 뿐이다.
- **zoom-out** — 에이전트에게 줌 아웃하여 낯선 코드 섹션에 대한 더 넓은 맥락이나 더 높은 수준의 관점을 제공하도록 지시한다.

---

### 생산성

코드에 특화되지 않은 일반적인 워크플로우 도구.

- **caveman** — 초압축 커뮤니케이션 모드. 불필요한 군더더기를 제거하면서 완전한 기술적 정확성을 유지하여 토큰 사용량을 ~75% 줄인다.
- **grill-me** — 결정 트리의 모든 분기가 해결될 때까지 계획이나 설계에 대해 집요하게 인터뷰를 받는다.
- **write-a-skill** — 적절한 구조, 점진적 공개(progressive disclosure), 그리고 번들된 리소스를 갖춘 새로운 스킬을 생성한다.

---

### 기타

보관하지만 거의 사용하지 않는 도구.

- **git-guardrails-claude-code** — 위험한 git 명령(push, reset --hard, clean 등)이 실행되기 전에 차단하는 Claude Code 훅을 설정한다.
- **migrate-to-shoehorn** — `as` 타입 단언(type assertion)을 @total-typescript/shoehorn으로 테스트 파일을 마이그레이션한다.
- **scaffold-exercises** — 섹션, 문제, 풀이, 그리고 설명자(explainer)를 갖춘 연습 디렉터리 구조를 생성한다.
- **setup-pre-commit** — lint-staged, Prettier, 타입 체크, 그리고 테스트를 포함한 Husky 프리-커밋 훅을 설정한다.
